## 摘要

Fault-tolerant quantum computing requires quantum error-correction (QEC) decoders that achieve low logical error rates under real-time operating constraints. These constraints motivate heuristic decoding algorithms whose error-correction performance must be evaluated through large-scale simulation. High-throughput decoding accelerates this evaluation and the exploration of decoder parameters. Using multiple graphics processing units (GPUs) is a natural way to scale these simulations, but naively distributing syndrome batches introduces host-side preprocessing and output-collection overheads that limit scaling. To address these limitations, we extend the Pêlagos relay belief-propagation (Relay-BP) decoder with process-isolated orchestration, parallel host preprocessing, and shared-memory output. We evaluate both one-gross ($[[144,12,12]]$) and two-gross ($[[288,12,18]]$) codes in a multi-GPU environment. Specifically, for the one-gross circuit at $R=50$, eight AMD Instinct MI300X GPUs and eight AMD Instinct MI355X GPUs achieve optimized end-to-end speedups of $5.68\times$ and $6.23\times$, respectively. For the two-gross circuit, the corresponding speedups are $6.92\times$ and $7.01\times$. When throughput is calculated using GPU decoding time, the corresponding two-gross speedups are $7.58\times$ and $7.45\times$, indicating near-linear GPU scaling. We deploy Pêlagos on Lux, Oak Ridge National Laboratory's AMD Instinct MI355X-based supercomputer, as a pathfinding application for high-throughput QEC simulation. This deployment provides a concrete quantum-computing use case for the AI + HPC infrastructure supporting the Genesis Mission's scientific-discovery goals. These end-to-end measurements demonstrate a practical path to accelerating large-scale QEC simulation through efficient multi-GPU decoding.

## I. INTRODUCTION

Fault-tolerant quantum computers will need logical qubits with error rates around 10−12 to run algorithms with billions of logical operations [1]. Quantum low-density parity-check codes, such as bivariate bicycle codes [2], promise to reach this regime with far fewer physical qubits than the surface code, but only if their decoders are both accurate and fast. Real-time constraints favour heuristic message-passing decoders such as relay belief-propagation (Relay-BP) [3], whose performance under circuit-level noise cannot be derived analytically and must be established by simulation. In this paper, we address these deficiencies jointly with one process per GPU, parallel host preprocessing, and shared- memory output. At relay depth R = 50, the integrated design achieves eight-GPU end-to-end speedups of 5.68× on AMD Instinct™MI300X and 6.23× on AMD Instinct MI355X for the one-gross ([[144, 12, 12]]) circuit, and 6.92× and 7.01× for the two-gross ([[288, 12, 18]]) circuit. For the two-gross circuit, throughput calculated using GPU decoding time scales by 7.58× on MI300X and 7.45× on MI355X. Host preparation, dispatch, and result handling limit end-to- end scaling. ## II. BACKGROUND

A. Relay-BP Introduction Relay-BP is a message-passing decoder for quantum low- density parity check (LDPC) codes [3], and is an adaptation of the belief propagation (BP) developed for decoding classical LDPC codes. It operates on a decoding graph, or detector error model, that connects error mechanisms to the detectors they trigger. Min-sum BP exchanges log-likelihood messages along these edges and tests whether the resulting error esti- mate reproduces the observed syndrome. Syndrome agreement establishes a valid candidate, but does not guarantee a correct logical outcome. On quantum codes, loops and degeneracy can produce oscillations and symmetric trapping sets that prevent BP from converging. For multiple GPUs, the existing design partitions the syn- drome batch into independent shards. Each GPU holds a graph replica and runs its own decode loop, with no message exchange between GPUs. Corrections are gathered after de- coding; Ray distributes work across nodes for larger simulation studies [7]. This decomposition provides the basis for our study. We retain the single-GPU kernels and layouts and optimize the surrounding node-local preprocessing, process ownership, and output collection. Relay-BP introduces disordered memory to address these failures. Each error node mixes its fixed prior with its previous marginal using a node-specific memory strength γj. Varying these strengths breaks symmetry; intervals including negative values help the decoder escape trapping sets [3].

## III. MULTI-GPU ORCHESTRATION

A. Context Ownership The original multi-GPU path constructs multiple GPU de- coders in one Python process and dispatches them through host threads. This organization keeps batch partitioning simple, but the parent process owns every HIP context. Process isolation therefore requires workers to establish device ownership before any process constructs a GPU decoder. Successive BP runs form relay legs, with each leg initialized from the previous leg’s final marginals. The first uses a shared γ0; later legs sample fresh strengths from a problem-specific interval. Decoding stops at the leg limit R or after finding S valid candidates, and returns the candidate with the lowest prior-weighted error cost [3]. The resulting algorithm achieves low error rates without requiring a second-stage decoder such as ordered statistics decoding (OSD) [10], [11]. For our S = 1 workload, each syndrome stops at its first valid candidate, making shard completion times data-dependent. Our process-isolated design gives each physical GPU one persistent worker process. The GPU runtime fixes its visible devices at initialization, so each worker sets its assignment before that point. It then sees one physical GPU, addresses it as a single logical device, and runs the unmodified single-GPU decoder. Workers start as fresh Python interpreters and ini- tialize the GPU runtime after setting their device assignment. The parent process holds no GPU context. Each worker also keeps a private compiler cache and, during tuning, a private measurement log. B. Pˆelagos Introduction Pˆelagos implements Relay-BP on GPUs for high-throughput QEC simulation [7]. Estimating logical error rates requires decoding many independent syndromes for the same circuit. Pˆelagos processes these syndromes in batches so that GPU kernels perform the same sparse graph operations across multiple decoding instances. ## V. RELATED WORK

M¨uller et al. introduced Relay-BP as a memory-assisted decoder for quantum codes [3]. Diamantopoulos et al. mapped Relay-BP to GPU kernels in Pˆelagos and evaluated its layouts, portability, decoder quality, and large-cluster deployment [7]. We build directly on that implementation and focus on process- isolated host orchestration rather than cluster-scale deploy- ment. CUDA-Q QEC provides a GPU-accelerated quantum low-density parity-check decoder that also implements belief propagation, ordered-statistics post-processing, and Relay-BP [16]. The published Pˆelagos study reports a comparison against CUDA-Q QEC on MI300X [7]. We do not repeat that compar- ison, and instead hold the decoder configuration fixed while varying only the orchestration. We also conduct a microarchitecture analysis by profiling both circuits on a single MI355X GPU. Larger batches in- crease measured GPU occupancy while reducing cache reuse (Table IV). Specifically, increasing B provides more inde- pendent syndrome work, but also enlarges the edge-message arrays of shape [E, B]. For one-gross, occupancy rises from 30.9% at B = 64 to 66.3% at B = 1,024 and 80.8% at B = 5,114. For two-gross, occupancy increases from 35.8% to 70.9% across the tested sizes. Meanwhile, from the smallest to the largest tested batch, L2 hit rates decrease from 57.5% to 42.9% for one-gross and from 65.2% to 52.5% for two-gross. Vector-L1 hit rates also decrease. Thus, larger batches expose more parallel work with lower cache-hit rates. General autotuning systems, such as OpenTuner and the tensor virtual machine (TVM) compiler, search implemen- tation spaces using measured objectives [17], [18]. Triton exposes tile, warp, and pipeline parameters for generated GPU kernels [12].
