A team serving a 9B-20B open-weight language model on vLLM or SGLang must choose a quantization recipe, and needs two numbers: the speedup over BF16 and the accuracy given up. We assemble every public measurement of these numbers that we could verify and find that the record supplies them only in pieces. Only two checkpoints, both INT4 builds of Gemma 3 12B, have both a vLLM timing and an accuracy score, and that score covers a single MMLU subject, one that the AWQ build was calibrated on. The batch-1 timings predate current engine releases, AMD and Intel Gaudi have no timing in this band at all, and FP4 has none against BF16. The timings that do exist follow one rule. Decoding a small batch is limited by memory bandwidth, so 4-bit weights roughly double speed (2.12x for Qwen2.5-14B on an A100), but the gain vanishes once a large batch makes the GPU compute-bound (1.02x for Gemma 3 12B at batch size 256), where FP8 is the recipe that can still help. Many published accuracy deltas, including every HumanEval delta, lie within benchmark sampling noise. We close with a seven-item reporting checklist for future measurements.

## 1 Introduction

Open-weight models of 9B to 20B parameters fit on one data-center GPU in BF16 and on one consumer GPU once quantized, which makes them a common choice for self-hosted serving. A team serving one on vLLM [15] or SGLang [49] must pick a quantization recipe for its GPU, and needs the speedup over BF16 and the accuracy given up. This letter asks whether the public record answers that question for Qwen2.5-14B, Qwen3-14B, Gemma 3 12B, Phi-4, Mistral NeMo, Ministral 3 14B, and gpt-oss-20b [1, 9, 20, 21, 23, 26, 27]. We kept a timing if its source named the engine, GPU, checkpoint, and workload, and an accuracy score if the same source reported a BF16 score from the same harness. We searched the vLLM, SGLang, AMD ROCm, and Intel Gaudi documentation, Hugging Face model cards from the model developers and from quantization publishers (Red Hat AI, PyTorch, Tencent AngelSlim), benchmark reports, and arXiv, pairing each model name with each recipe (FP8, INT8, AWQ, GPTQ, INT4, NVFP4, MXFP4) and each engine, up to 5 October 2026. An AI coding assistant helped collect the sources and extract the numbers; every number was then checked against its cited source on 5 October 2026. The record answers it only in pieces, and we make three contributions. We explain the timings that do exist with one memory-versus-compute rule (Section 3). We show that many published accuracy deltas are smaller than the sampling noise of their benchmarks (Section 4). We grade what the evidence supports and propose a reporting checklist to close the gaps (Sections 5 and 6). Earlier work covers parts of this question. Surveys cover quantization before today’s serving stacks [10] and efficient LLM inference broadly [50], and Zhao et al. benchmark post-training algorithms on quality alone [48]. Kurtic et Smit Kadvani, Kriti Faujdar, and Spurthi Tallam, Independent researcher, United States.

## 2 Recipes and engine support

A recipe is written W𝑥A𝑦: weights stored in 𝑥 bits, matrix multiplications run on 𝑦-bit activations. Weight-only INT4 (W4A16) dequantizes 4-bit weights into a 16-bit matmul. GPTQ (published as OPTQ) chooses the integers with a one-shot second-order reconstruction [7], AWQ rescales the channels that see large activations [17], and the Marlin kernel runs the dequantized matmul, reporting up to 2.8× end-to-end speedup inside vLLM [8]. W8A8 also quantizes activations, so the matmul itself runs in 8 bits: LLM.int8() routes outlier features to a 16-bit path [5], SmoothQuant migrates them into the weights [47], and FP8 uses the E4M3 format [19]. FP8 activation scales are either fixed after calibration (static) or computed per token at run time (dynamic). MXFP4 stores 4-bit floats in blocks of 32 that share a power-of-two scale [41]; NVFP4 is NVIDIA’s 4-bit float format, executed natively on Blackwell [43]. Engine support depends on the GPU. vLLM runs FP8 W8A8 on Ada, Hopper, and AMD but not on Ampere, where its Marlin kernels still serve GPTQ, AWQ, and FP8 checkpoints as weight-only [46]. SGLang supports fp8, awq, and mxfp4 on AMD Instinct MI300X and later, and keeps its Marlin kernels CUDA-only [43]; AMD documents FP8 and Triton AWQ for vLLM [2]. 3 Performance: one rule explains the timings Table 1 has every in-band timing we found: four engine–GPU groups, each with its own model and metric, so speedups compare within a group only. A memory-versus-compute (roofline) view explains all of them. At batch size 1, each generated token reads every weight once, so decode time is set by bytes moved, and 4-bit weights move a quarter of the bytes of BF16. That is why every INT4 recipe is 1.35–2.12× faster at batch size 1; the gain falls short of 4× because dequantization, attention, and KV-cache reads do not shrink. At batch size 256, one read of the weights serves 256 sequences, the matmuls become compute-bound, and W4A16 still computes in 16 bits, so Gemma 3 12B gains only 1.02×. Long prompts are compute-bound for the same reason: the A100 INT4 gain falls from 2.12× to 1.64× at a 30,720-token prompt, and on the H20, whose metric counts prompt tokens, FP8 pulls ahead of AWQ (1.68× versus 1.42×) because Hopper’s FP8 tensor cores run at twice the BF16 rate [22]. The rule predicts that FP8 keeps a speedup at large batch where INT4 loses it, but no in-band source tests FP8 above batch size 1. gpt-oss-20b is a different case: a mixture-of-experts model with 20.9B total and 3.6B active parameters, post-trained with MXFP4 expert weights [23]. Its only in-band timing compares engines, not recipes: at default settings, vLLM delivers 2.93× the total throughput of SGLang on the same prompts, and the same report raises vLLM to 19,128.79 tokens/s with asynchronous scheduling [11]. No BF16 timing exists, although MXFP4 values are exactly representable in BF16 at realistic block scales, so a BF16 copy would have the same accuracy. ## 5 What the evidence supports

Table 3 grades each claim. For latency-bound serving at small batch, W4A16 cuts per-token latency by a quarter to a half and costs about one MMLU point; check GSM8K, which loses up to four. For throughput-bound serving at large batch, INT4 is a memory choice, taking a 14B model from about 28 GB to about 10 GB, and FP8 is the recipe the roofline favors, but no public in-band timing confirms it. On Ampere, FP8 checkpoints run only as weight-only, so the roofline predicts gains like GPTQ-Int8’s 1.52×, not INT4’s.

## 6 A reporting checklist

Several gaps above trace to details a source omitted rather than to experiments nobody ran. A quantized-serving claim answers the practitioner’s question if it reports: (1) one checkpoint ID and revision, used for both timing and accuracy; (2) engine, version, and every non-default flag; (3) GPU model and count; (4) input and output lengths, batch size or request rate, and whether throughput counts prompt tokens; (5) a BF16 baseline timed on the same stack; (6) harness, version, few-shot count, chat template, and reasoning mode, with 𝑛 and standard errors; (7) the calibration data, confirmed disjoint from the evaluation sets. No source in this letter meets all seven: none reports standard errors, and only the Gemma card times the checkpoint it scores.

## 7 Limitations

The rows in Table 1 come from different experiments and are not one benchmark. Our standard errors assume independent questions and a single run. The Qwen FP8 checkpoint used for timing is quantized in blocks of 128 [28], but its activation scaling is not stated, so it cannot be matched to the static or dynamic accuracy rows. All web sources are vendor or project pages that can change; they were last checked on 5 October 2026.
