## 摘要

Large language models (LLM) have been the key focus of recent machine learning breakthroughs. As the model size grows exponentially, the computation needed for training is astronomical. A GPU can do a huge amount of arithmetic. However, the data its compute units need is not always available when they are ready. This data may still be in slow memory or on another GPU. While the chip waits, expensive compute sits idle, and at scale even a small drop in utilization translates into substantial cost. In this paper, we treat this waiting time as the primary bottleneck. We focus on hardware features designed for explicit data movement. These features load data from off-chip memory onto the chip, rearrange it into the layout the computation requires as it is loaded, and transfer it between GPUs. By orchestrating them, we keep a steady pipeline of data flowing to the compute units so that they remain busy. We present kernel and framework implementations that address this bottleneck using three key data-movement instructions and hardware features. The Tensor Data Mover (TDM) moves tensor data from high-bandwidth memory (HBM) into on-chip memory. Transpose-load instructions transpose tensor data into the layout that LLM computations require as it is loaded on-chip. Finally, System DMA (SDMA) and Remote DMA (RDMA) move data between GPUs over the scale-up and scale-out networks, respectively. Our results show that TDM and transpose-load provide on average 1.88x and 1.19x speedup at the kernel level, respectively. The SDMA and RDMA lead to on average 1.16x and 1.33x speedup for computation overlapped with communication. This is the first AMD LLM training system to utilize all the GPU data pipelining features. ## 1
Introduction

Recent years have witnessed an exponential surge in LLMs. People are training larger and larger models with an unprecedented amount of data. As the training grows exponentially, the amount of computation needed is unprecedented in human history. People are building larger and larger GPU clusters to train LLM models, due to both the model size and the amount of computation. There have been many reports on GPU under-utilization in the industry [13, 18, 19]. For hyper-scale users, even one percent of efficiency can mean millions of dollars. From a hardware perspective, Hierarchical Data Pipelining for LLM Training on AMD GPUs Rao et al. under-utilization can arise from several sources, including hardware failures [15], power constraints [30], and data-movement overheads [14, 27], which become increasingly significant as models and distributed training systems scale. In this paper, we focus on data-movement overhead as a source of GPU under-utilization. Within a GPU, compute units may stall while waiting for data or spend execution resources moving and transforming it. Across GPUs, communication may consume compute resources or delay dependent computation. We consider these two cases separately as intra-GPU and inter-GPU data movement. Intra-GPU data movement. Traditional GPU programming emphasizes that GPUs hide long memory-access latency through inexpensive thread switching, i.e., scheduling more threads than the hardware can execute at once [26]. In recent years, however, software-managed data pipelines have become an increasingly important complementary approach to latency hiding. A key driving force behind this shift is the co-evolution of GPU hardware architectures and kernel algorithm design. Consider attention kernels, underpinning the Transformer architectures central to recent breakthroughs in large language models (LLMs) [25]. Modern high-performance attention kernels largely follow the approach introduced by FlashAttention [11]: keeping the softmax state and output accumulators on-chip while streaming key and value tiles from memory. Although this approach avoids materializing the full attention matrix and significantly reduces global memory traffic, it introduces a new performance challenge of efficiently orchestrating data movement between global and on-chip memory. In particular, attention computation requires fine-grained scheduling of KV tile loading, data transformation, and computation to prevent memory latency from stalling the execution units. On older GPU architectures, transferring data into on-chip memory requires explicit load instructions executed by threads on the compute units. As a result, data movement competes with computation for execution resources. While one group of threads waits for memory operations to complete, another group performs useful computation. However, this approach becomes increasingly challenging for attention kernels, where limited on-chip memory capacity and frequent data transfers demand tighter coordination between memory operations and computation. Recent GPU architectures are beginning to address this challenge. For example, AMD’s MI455 introduces the Tensor Data Mover (TDM), which moves data between HBM and on-chip memory. This not only allows software-managed data pipelines to be offloaded to hardware DMA engine, but also introduces new fine grain instruction set architecture (ISA) to coordinate between memory transfer and computation, fundamentally changing the optimization target from “launch enough threads to hide a high-latency load” to “build a steady stream that keeps the compute units fed.” A similar trend can be observed in data transformation. During LLM training, tensors frequently require different layouts for forward and backward computations, making matrix transposition an important source of overhead. On MI355, specialized matrix-transpose instructions allow data to be transposed during loading, eliminating the need for explicit register-level transposition by the compute units [1]. We will detail our implementation and the performance impact of these ISA changes in Section 3.1. Our implementation shows that matrix transpose leads to on average 1.19× and up to 1.21×. TDM leads to on average 1.88× and up to 2.74×. Inter-GPU data movement. As large-scale LLM training expands to thousands of GPUs, inter-GPU data movement has become an increasingly important performance bottleneck. At first glance, overlapping communication with computation appears straightforward: ideally, network transfers proceed concurrently with GPU computation, achieving both high network bandwidth and high compute utilization. In practice, however, communication and computation often compete for the same GPU execution resources, making effective overlap much more challenging. For example, traditional RCCL-based communication from AMD can occupy up to 64 compute Hierarchical Data Pipelining for LLM Training on AMD GPUs Rao et al. units (CUs), corresponding to 25% of the compute resources on MI355. Consequently, even when communication is fully overlapped with computation, we can observe significant slowdown in compute throughput. This reveals a fundamental limitation of conventional GPU-driven communication: hiding communication latency does not necessarily eliminate its computational overhead. One possible workaround is to increase the local batch size, thereby performing more computation per communication operation and amortizing communication overhead. However, this approach conflicts with the growing demand for faster distributed training. For customers renting GPU clusters in the cloud, time-to-train is often as important as overall hardware efficiency. For example, assuming near-linear scaling, training a model on more than 2,000 GPUs in two months may be preferable to training it on 1,000 GPUs over four months. Achieving such scaling requires maintaining high efficiency at smaller per-GPU batch sizes, where communication accounts for a larger fraction of execution time. Therefore, simply increasing the amount of local computation is not always a viable solution. To address this challenge, AMD GPUs and Network Interface Cards (NICs) provide dedicated DMA engines for inter-GPU data movement, including System DMA (SDMA) and Remote DMA (RDMA). Unlike traditional communication kernels that consume GPU compute resources, these engines enable data transfers to proceed independently of the compute units, creating opportunities for more effective communication–computation overlap. To make these capabilities accessible, we have been introducing lightweight, DMA-based communication APIs across multiple layers of the ROCm software stack. These APIs expose dedicated data-movement engines through programmer-friendly interfaces, supporting both high-level collective operations in PyTorch and low-level, customized communication implementations. We will provide detailed evaluation of overlapping overhead in Section 4.4 and detail our hardware support and software API in Section 3. Our results show that System and Remote DMA based optimization leads to on average 1.16× and 1.33× of overlapped computation with communication.

2.1 Attention Kernel Attention is a core operation in modern large language models [25]. For a sequence of T tokens, each attention head projects the input activations into the query, key, and value matrices Q, K ∈RT×d and V ∈RT×dv, where d and dv denote the key/query and value dimensions, respectively. This algorithm makes the timing of the streamed K, V tiles critical and turns attention optimization into a tiled dataflow problem: we need to fetch each tile of K and V in time, so that the computing units are always busy. To make this issue more complex, as the industry is starting to use longer and longer sequence lengths, more attention variants have been proposed to address the HBM memory bandwidth issue: • Sparse Attention: It restricts each query to a selected subset of keys and values, and can also reduce memory traffic and computation. The recent DeepSeek V4 model proposed Compressed Sparse Attention (CSA), which uses the two optimizations mentioned above [28]. This creates additional challenges to kernel implementation, as the dataflow is more irregular: Each query token receives a top-k list containing a sliding-window component and, depending on the compression ratio, additional compressed latent vectors. The forward pass must gather those vectors, compute scores, and stream the corresponding values into the output accumulator. The backward pass is more demanding: it must gather the same sparse vectors to form dQ, produce a per-token/per-slot intermediate for dKV , and then reduce that intermediate by the inverse of the top-k map [17, 28]. The kernel case study in this paper focuses on this new sparse attention algorithm, as it represents one of the most challenging data movement patterns in LLM training and represents a possible direction for the future evolution of attention algorithms. 2.2 Communication for LLM training In recent years, as LLM sizes and architectures evolve, parallelism and communication pattern have also changed. The traditional parallelism strategy includes data parallelism and data shard- ing, including ZeRO sharding, FSDP [23, 31]. Other forms of parallelism include tensor parallelism (TP) [24], context parallelism (CP) [20], etc. As the MoE architecture has become more popular, targeting parallelism and communication patterns have also emerged (e.g., DeepEP [29] and the All2All communication), also more recently MegaMoe kernel [12], which fused communication with computation. In this paper, we focus on the traditional FSDP pattern. For a pipeline of depth N, we can start the pipeline with N+1 tensor loads and simply check S WAIT TENSORCNT with N. Because tensor-movement instructions complete in-order with other Tensor instructions from the same wave (both loads and stores stay in-order), we can ensure the data is ready without worrying about memory transfer ordering [4]. The important programming property is that the gather is not expressed as a loop of vector global loads into LDS. And the programming mindset changes from “launch enough workgroups to hide a high-latency load” to “build a steady stream that keeps the compute pipeline fed.” This also lowers the occupancy and frees more registers for the kernels, so more data can be reused in registers. Our kernels read eight indices with one scalar load and pass them to TENSOR LOAD TO LDS. This change enables a deeper pipeline and higher data reuse in the register. MI455 architecture also introduces an asynchronous load instruction from HBM to LDS, GLOBAL LOAD ASYNC TO LDS. ## 5
Related works

AMD GPU also provides other data-pipelining ISA and features, such as prefetching from HBM to different cache layers. This feature has already been utilized in our kernel implementation. TDM can move data from HBM of other GPUs in the scale-up network to the on-chip memory of the local GPU, and vise versa. Recent AMD work has enabled using TDM for tightly-coupled communication and computation, such as DeepEP and MegaMoE kernels.

## 6
Future works

Recent AMD work has been exploring reverse offloading for GPU communication, which utilizes proxy threads on the host CPU to initiate network operations. This gives us a new low overhead programming method for implementing GPU communications that are coupled with computation. Hierarchical Data Pipelining for LLM Training on AMD GPUs Rao et al. We will explore this method to implement DeepEP and MegaMoE kernels. We will also continue to explore hierarchical System and Remote DMA based communication collectives and integrate it to our LLM training framework.

## 7
Conclusion

This paper presents data pipelining features of AMD GPU. The Tensor Data Mover (TDM) moves tensor data from HBM to on-chip memory. Transpose-load instructions transpose tensor data into the layout that LLM computations require as it is loaded on-chip. System DMA and Remote DMA move data between GPUs over the scale-up and scale-out networks. We show that these data pipelining features enables a rethinking about GPU efficiency. We need to schedule the data movement across the GPU system (e.g., from HBM to on-chip memory and between local and remote HBM) in time, so the compute units are always busy and not wasted for waiting or moving the data. It is also infeasible to prefetch everything needed to the closest memory hierarchy. The on-chip memory and HBM capacity are too small compared to the huge memory capacity needed for LLM training. We utilize these features in our library and framework implementations for LLM training. Our evaluations show speedup on average 1.88× for TDM, 1.19× for Transpose-load. For overlapped compute with communication, 1.16× for System DMA and 1.33× for Remote DMA.
