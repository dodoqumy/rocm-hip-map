## 摘要

Each new GPU generation is showcased by its peak instruction rates, yet users hardly ever run instructions directly: they reach the hardware's performance through vendor libraries, applications and devices shared with other jobs. How much of a theoretical speedup survives these layers is rarely measured, so a team deciding whether to move to a new generation, or to adopt FP8 or 2:4 sparsity, lacks adequate guidance. AMD's MI300A (CDNA3) adds new FP8 matrix instructions and 2:4 structured-sparse instructions that the predecessor, the MI250X (CDNA2), does not have. We analyze this theoretical speedup gap on AMD's MI300A (CDNA3) against the MI250X (CDNA2) by defining a new metric, capability gain. Capability gain is the fraction of a feature's instruction-level speedup that it keeps at a higher level, such as a library, an application or a shared device. We trace it from ISA microbenchmarks through hipBLASLt and hipSPARSELt to LLM inference and mixed-precision HPL, and onto a device shared by up to eight concurrent streams. FP8 keeps most of its speedup through the library, completing an $8192^3$ GEMM \genCapPkgEndToEndGainEightK{} faster than the MI250X with FP16, but unfused quantization turns it into a per-layer slowdown in an LLM, and 2:4 sparsity keeps at most about half of its speedup in hipSPARSELt. Under queue sharing, FP8's GEMM capability gain rises above 1. How fairly streams share the device depends on the number of hardware queues, not on the numeric precision, yet shared LLM serving gains nothing from FP8.

## I. INTRODUCTION

Recent GPU generations increase matrix throughput mostly through narrower formats and structured sparsity. Deep learn- ing uses FP8 [1], [2] and 2:4 sparsity [3], and HPC solvers now use mixed precision [4], [5]. Vendors advertise each feature by its peak instruction rate, but users reach it through libraries and applications. Before adopting FP8, 2:4 or a new generation, users need to know how much of that rate their own code gets. To our knowledge, this is the first study to measure FP8 and 2:4 on AMD hardware against the previous generation, and the first to measure sharing on both generations under one protocol, with the number of hardware queues (4 or 16) as a controlled variable. AMD added FP8 and 2:4 structured sparsity to its CDNA3 GPUs. El Capitan, the TOP500’s fastest system from Novem- ber 2024 to June 2026 [6], [7], is built on CDNA3’s MI300A APU, and Frontier, still in production, is built on CDNA2’s MI250X, which has neither feature. On paper, a CDNA3 compute unit (CU) can do 2× the FP16 matrix work per cycle of a CDNA2 CU, 4× with FP8, and 8× with FP8 and 2:4 sparsity [8]–[10]. We time each hipSPARSELt stage, test a break-even model on held-out shapes, and run the hardware 2:4 path under sharing.

4) Break-even model: A cost model built from each stage predicts the pruning cost, but not the break-even point. Sparsity pays off only when the matmul runs on enough columns N to cover the cost of pruning and compressing the weights once. Pruning and compression both scale with the weight size: Tprune = a MK and Tcomp = b MK, with c = a + b. Planning costs a constant γ, and each matmul runs at its measured peak rate, T = 2MNK/R, with Rde for dense and Rsp for sparse. The break-even width N ∗is where the one-shot sparse total, which pays every stage once, equals the dense matmul: For RQ3, the boundary is the hardware-queue pool: it, not precision, sets fairness on a shared device: with enough queues the pool treats every precision equally, and the default four queues trade fairness for throughput. FP8’s speedup over FP16 grows when streams share queues, and the growth tracks a larger clock drop for FP16. 2:4 sparsity also tends to gain under sharing, and hard partitions isolate streams better than CU masks. 1) Metrics: Three metrics compare each stream’s shared wall time with its solo time. Jain’s index J [39] measures how evenly sharing slows the streams; it is 1 when all slow down equally, and we compare it only across streams that run the same GEMM. System throughput (STP) sums each stream’s solo-over-shared time, so it reaches n for n perfectly overlapped streams and is 1 when sharing is no faster than running them one after another. Average normalized turnaround time (ANTT) is the mean shared-over-solo time, that is, the average slowdown.
