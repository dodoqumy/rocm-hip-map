## 摘要

Achieving performance portability is challenging for irregular scientific applications built as repeated multi-kernel GPU pipelines, because throughput depends on out-of-kernel decisions as much as on kernel efficiency. Using molecular docking as a representative case study, we propose an out-of-kernel tuning methodology that treats batching policy, worker concurrency, and per-worker memory allocation as explicit optimization parameters, replacing backend-dependent occupancy-driven choices with a more portable execution strategy based on explicit resource bounds. We implement this methodology in the muDock mini-app under a manager/worker execution model where multiple host workers share a GPU through independent streams. We then evaluate the methodology on NVIDIA, AMD, and Intel GPUs across CUDA, HIP, and SYCL implementations. Across all evaluated platform/backend pairs, the memory-bounded formulation exceeds the peak throughput of the occupancy-guided baseline. The fully tuned methodology improves the end-to-end throughput on all tested configurations, achieving an average speedup of 1.53x over the baseline.

## I. INTRODUCTION

In this paper, we study this problem using muDock [12], [13], a compact molecular docking mini-app designed to preserve the key computational patterns of larger docking codes while enabling systematic experimentation across platforms and backends. Our goal is to study whether a more portable out-of- kernel formulation can improve throughput in a repeated multi- kernel GPU pipeline. Instead of relying on occupancy-driven batch sizing, which depends on backend-specific information and assumptions, we study an alternative formulation based on explicit resource bounds. In particular, we focus on batching policy, worker concurrency, and per-worker memory allocation as coupled tuning dimensions, and evaluate how these choices transfer across CUDA, HIP, and SYCL implementations. High-performance computing (HPC) plays a central role in reducing the time-to-solution of large-scale scientific ap- plications. As production systems increasingly rely on GPU acceleration, however, achieving this objective across different vendors and software ecosystems becomes more difficult in practice. Deploying a scientific application across platforms requires not only functional portability, but also tuning choices that remain effective despite differences in compilers, runtimes, and hardware resource behavior [1]–[3]. This problem is particularly relevant for applications that are not dominated by a single monolithic kernel, but instead execute long sequences of repeated kernel launches. In these applications, throughput depends on how inputs are grouped and submitted across the full pipeline, not only on the efficiency of one kernel in isolation. As a result, achieving portable performance requires looking at the full application pipeline, not only at kernel-level code generation. This work makes the following contributions: • We study an out-of-kernel tuning approach for repeated multi-kernel GPU pipelines based on explicit resource bounds, treating batching policy, worker concurrency, and per-worker memory allocation as the main tuning dimensions. The rest of the paper is organized as follows. Section II introduces the workload and portability context. Section III presents the batching policies and tuning dimensions studied in this work. Section VIII concludes the paper. muDock uses a manager/worker execution model. In this context, a worker is a host process pinned to a CPU core and associated with one execution device selected by the user from the command line. The device can be either a GPU or a CPU core. For a GPU, the runtime can spawn multiple workers for the same device. For a CPU execution path, the runtime instead uses one worker for each CPU core. In this paper, it is assumed that the main compute power is provided by the GPUs of the node, and assigning workers on CPU is omitted.

## II. BACKGROUND

We use this model as a straightforward way of tightly coupling the different resources (data, compute, memory). Of course, there is a multitude of other approaches in the context of task-based runtime systems and performance portability frameworks to coordinate different kinds of resources, and even combinations [16]. However, the molecular docking workload allows for a straightforward one-dimensional partitioning of all the work, by grouping into batches. There are no data dependencies that warrant a complex task graph. Thus, by focusing on the manager/worker model, one can avoid unnecessary synchronization and data movement: every worker is responsible for a single GPU stream. Still, the presented insights should be largely transferable to the wider context of task-based runtime systems on GPU workloads. Drug discovery is a long and costly process with a high failure rate. One of the challenges is the sheer size of the chemical space that we can explore to find a promising drug candidate [14]. To mitigate this problem, a recent trend introduces an in-silico step that virtual screen a chemical library of ligands, to find the most promising ones to test in-vitro. Recent studies demonstrate how increasing the number of virtual screened ligands, increases the probability of finding good drug candidates as well [9]. In the context of a virtual screening campaign, it is of paramount importance to maximize the number of virtual screened ligands within the computation budget. For this reason, we can capitalize on every optimization opportunity by evaluating more ligands, instead of reducing the time to solution, making virtual screening a relevant example of an irregular throughput-oriented workload.

## III. METHODOLOGY

To study this problem in a controlled setting, we use muDock as a compact molecular docking mini-app designed for benchmarking and portability studies. It preserves the main computational structure of larger docking codes while remain- ing compact enough to support systematic experimentation across platforms and backends. This section describes the out-of-kernel knobs that we investigate in this paper. While they are evaluated in the context of muDock, they are agnostic with respect to the mechanism used to orchestrate the computation. At a high level, our study focuses on two complementary aspects of the out-of-kernel execution strategy. The first aspect concerns how the work is grouped into batches under explicit resource constraints. The second aspect concerns how the workers coordinate and submit these batches to the GPU to overlap data transfer with computation and ensure that the pipeline remains busy. In this work, these two aspects are jointly analyzed rather than in isolation, because the effect of batch sizing depends on how much work can be kept in flight through concurrent submission and memory partitioning across workers. From the application point of view, muDock docks each ligand independently from the others, making the workload embarrassingly parallel. Docking a ligand means estimating the 3D displacement of its atoms when they interact with the target protein. To reach its goal it uses a genetic algorithm approach. Each individual’s genes encode geometric transformations to the ligands atoms. In particular, from the initial ligand pose, we encode in the first six genes the rigid rotations and translations along the x, y, and z axis. The other genes encode the angles of the ligand’s rotatable bonds. To evaluate the fitness of a population individual, muDock uses a scoring function that is functionally equivalent to the AutoDock force field described by Huey et al. [15]. It is common to use W host workers that enqueue kernels on the same device. In muDock, a manager owns the shared input backlog and the shared output queue. The input backlog contains the ligand descriptions that still need to be processed, while the output queue collects the completed results produced by the workers. The manager spawns one or more workers according to the selected devices and backends. Each worker repeatedly removes work descriptions from the shared input backlog, prepares the corresponding input data, and stores it in a local reordering buffer. The role of this local buffer is to group inputs with similar features before forming the next batch, reducing the imbalance inside the same device submission. When the inputs accumulated in the local buffer satisfy the batching rule of the selected method, the worker forms a batch and submits it to the device. The worker then executes the target pipeline for all inputs in that batch and writes the completed results to the shared output queue. This process continues until the input backlog has been drained. Increasing W can improve overlap and reduce launch-related idle time, but it also reduces the memory M available to each worker and may increase contention. For this reason, the worker count and the per-worker memory budget are part of the methodology itself rather than fixed background settings. 1) Explicit synchronization: An established approach uses explicit synchronization between two workers to implement double buffering [10]. The idea is that while one thread is executing a computation kernel on a buffer, another worker is transferring data to a second buffer. Once the kernel is completed, the second worker can issue its own computation kernel and the first worker can transfer data. This can be easily generalized to W workers. The benefit is that with this approach the developer is certain to overlap data transfer and computation regardless of the backend used to offload computation. The drawback is that a worker needs to wait for another kernel to complete before launching its own kernel. For this reason, this policy is usually paired with occupancy-guided batching [11] to maximize the computation efficiency. c) Workloads: The application performance is highly input-dependent, as the execution time is strongly related to the number of heavy atoms and rotamers [7]. For this reason, the study focuses on the heterogeneous mixed_n500k workload, built as a subsample of 500,000 compounds from the MEDIATE dataset [17]. The selected ligands are representative of different combinations of heavy-atom counts and rotamer counts, so that the workload preserves the irregular behavior that drives the batching problem. At the same time, the sampled distribution is intentionally biased toward a higher presence of smaller ligands than larger ones, to better reflect a common screening scenario in which lighter compounds are more frequent than the most complex molecules. All policy sweeps, headline comparisons, and portability results discussed in the paper are therefore derived from this mixed workload. 2) Concurrent execution: An alternative way relies on GPU streams and the underlying driver to overlap data transfer with computation. With this approach, each worker enqueues data transfer and computation kernels in a stream independently. For example, in case of the CUDA backend, a stream is represented by the CUDA stream. However, also the other backends expose to the developer a similar runtime to launch kernel concurrently. The benefit is that the resulting implementation is simpler, and it is possible to overlap data transfer and computation across the whole execution. The drawback is that the ability of maximizing the efficiency is up to the backend runtime and the underlying GPU driver. This policy can be paired with memory-bounded batching to maximize the number of in-flight ligands on the device. d) Throughput metric: Throughput is the main perfor- mance metric of interest for the end user, since it directly estimates how many ligands can be screened within a fixed time budget. Runs are monitored over time through observer samples. For each experiment, we report the throughput measured when the input backlog has been drained, namely when all ligands have either already completed or are in flight inside the pipeline. This choice lets us compare experiments that complete naturally with experiments that are stopped after a fixed timeout, without penalizing runs whose input queue empties early. We introduce a timeout of 5 minutes to keep the campaign duration reasonable, after observing that the pipeline reaches a stable saturation regime well before that limit in the valid configurations. Each experiment is executed five times; we discard the first run as warm-up and average the remaining four. If one of the five repetitions fails, for example, because the selected configuration exceeds the available memory budget, we discard the entire set of repetitions and mark that experiment as not available (N/A). As a consequence, missing points in the worker/memory and bucket-multiplier plots correspond to configurations for which at least one repetition could not be completed, typically because the requested batching and worker configuration required more device memory than the device could provide.

## VII. RELATED WORK

Molecular docking and virtual screening have long been driven by the tension between search accuracy and throughput. Classical docking systems such as AutoDock4 and AutoDock Vina established the structure still used in many workflows: repeated evaluation of large ligand sets under irregular search dynamics [4], [5], [19], [20]. Recent work has increasingly used HPC to speed up virtual screening campaigns and reduce their time to solution, while also targeting larger molecular libraries and more heterogeneous systems [7]–[9], [21], [22]. This is the application context of our work. Our focus, however, is not docking accuracy or scoring-model design, but the systems problem of sustaining portable throughput across heterogeneous GPU backends. Finally, our study is embedded in the wider performance- portability literature. Pennycook and coauthors formalized performance portability as a joint requirement of efficiency and portability, and follow-on work has emphasized that eval- uating portability requires more than demonstrating functional correctness across programming models [1], [2]. Subsequent cross-platform studies have reinforced this point for both full applications and benchmarking suites, including recent work on programming-model comparisons and on SYCL behavior across NVIDIA, AMD, and Intel platforms [29]–[31]. Our contribution is deliberately narrower and more application- driven: we isolate one consequential out-of-kernel policy question in a repeated multi-kernel scientific workflow and show how a portable methodology can improve throughput while also revealing the remaining limits imposed by backend- specific behavior. Recent GPU docking work has made that systems dimension increasingly explicit. AutoDock-GPU and related studies show that docking is not only compute intensive but also structurally irregular, with performance shaped by ligand-dependent search behavior, batching choices, and host-device interaction [23], [24]. Other modern GPU docking engines, such as Uni- Dock, push throughput further through aggressive batching and GPU-oriented dataflow design [18], while comparative studies in earlier GPU docking work show that different mapping strategies can shift the balance between latency and throughput [10]. Our paper is closest to this systems-oriented branch of docking research, but differs in focus: rather than proposing a new fastest docking engine, we study how batching and worker-level resource decisions transfer across CUDA, HIP, and SYCL implementations.

## VIII. CONCLUSION

This paper presented a portable out-of-kernel optimization methodology for scientific applications organized as repeated multi-kernel GPU pipelines, and studied it through the muDock molecular docking mini-app. More generally, the paper shows that for similar irregular throughput-oriented workloads, appli- cation throughput can be improved by tuning three coupled runtime dimensions: the memory allocated to each worker, the batching policy used to form the next execution chunk, and the number of workers that concurrently feed the device. This work builds on the out-of-kernel perspective introduced in prior docking studies [10], [11]. The main idea is that performance portability is shaped by policy choices outside the kernels themselves, such as bucketing, batching, and stream- level concurrency. These choices are especially delicate on heterogeneous GPU platforms, where occupancy information, register usage, and runtime behavior differ across CUDA, Across the investigated platforms and backends, this method- ology improves the mixed-workload throughput by 1.53× on average over the monolithic reference configuration. At the policy level, the memory-bounded batching method matches or exceeds the peak throughput of the occupancy-guided method on every evaluated platform/backend pair. These results indicate that tuning memory allocation, batching, and worker concurrency together provides a practical way to improve throughput while preserving portability across CUDA, HIP, and SYCL implementations.
