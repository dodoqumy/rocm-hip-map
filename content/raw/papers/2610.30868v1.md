## 摘要

Data-intensive GPU applications increasingly rely on NVMe SSDs to extend GPU memory. NVIDIA GPU Direct Storage (GDS) enables direct SSD-GPU transfers via PCIe peer-to-peer DMA, eliminating host staging. However, GDS retains three key limitations: (1) its control path traverses the kernel for every I/O request, introducing software overhead; (2) its stream-ordered path imposes strict total ordering even when workloads only require batch-level ordering; and (3) its closed-source user-space engine hinders diagnosis and custom scheduling. We present uGDS, https://github.com/ScaleX-IO/uGDS, an open-source user-space GPU Direct Storage library built on four principles: user-space control, unified cross-vendor abstraction, workload-aware scheduling, and end-to-end transparency. The host CPU manages the entire NVMe command lifecycle in user space, while payloads move via PCIe P2P DMA without consuming GPU compute. A minimal kernel module (ugds_drv.ko) is used only for one-time privileged setup. uGDS partitions hardware queues between synchronous and batch traffic, enforces DMA-safe buffer lifetimes, and provides cuFile-compatible synchronous, batched, and stream-ordered APIs with polling or interrupt completion on both NVIDIA CUDA and AMD HIP. Evaluated on an A100 with a Samsung 990 PRO, uGDS achieves up to 12.12x GDS's batch-read bandwidth and 30.69x its batch-write bandwidth (8- and 4-KiB requests, batch size 128), and reduces 4-KiB synchronous write latency by 84.1% with two threads. Its stream-ordered path sustains 5.49 GiB/s on a single stream, where GDS retains only 40.8% of its synchronous bandwidth. In LMCache, uGDS reduces median time-to-first-token (TTFT) by up to 62.7% and raises serving goodput by 2.63x. On AMD, uGDS achieves up to 1.19x hipFile's synchronous-write bandwidth.

## Keywords

Data-intensive GPU applications, including LLM KV-cache offload- ing, vector search, and large-scale analytics, increasingly rely on NVMe SSDs to extend limited GPU memory capacity and support on-demand data movement. As models and datasets continue to grow beyond GPU memory capacity, efficiently transferring data between SSDs and GPUs has become critical to application per- formance. NVIDIA GPU Direct Storage (GDS) enables direct data transfers between NVMe SSDs and GPU memory through PCIe peer-to-peer DMA, eliminating intermediate copies through host memory. However, removing host staging alone does not eliminate software overheads or provide the flexibility required by diverse GPU workloads. Three key limitations remain: (1) the control path still traverses the kernel for every I/O request, introducing unnec- essary software overhead; (2) stream-ordered I/O path incurs signif- icant overhead and enforces a total order even when applications require ordering only at batch granularity; and (3) closed-source user-space I/O engine limits performance diagnosis and prevents applications from adapting I/O scheduling to their access patterns. Introduction

Today’s GPU applications face both a memory-capacity wall and a bandwidth wall. As large language models and context windows out- grow HBM capacity, inference engines move tensors and KV caches across GPU, host, and storage tiers [1–3]. GPU vector search like- wise relies on efficient movement and placement of large indexes [4]. Training systems such as ZeRO-Offload and ZeRO-Infinity extend GPU memory with CPU memory and NVMe storage [5, 6]; Deep- Speed Inference combines model partitioning and offloading to serve models beyond a single GPU’s capacity [7]. These workloads make NVMe SSDs a useful intermediate storage tier. In these work- loads, the direct SSD-to-GPU transfer path lies on the critical path: every additional microsecond of software overhead becomes GPU idle time and can reduce compute utilization. The conventional storage path is ill-suited to applications that move large amounts of data between GPUs and SSDs. Requests traverse the kernel NVMe driver, a filesystem, and often a host staging buffer, incurring system calls, context switches, page-cache or bounce-buffer copies, and synchronization. NVIDIA’s GPU Direct Storage (GDS), exposed through cuFile [8, 9], removes host staging from the data path: the SSD transfers data directly to or from GPU memory through PCIe peer-to-peer DMA [14]. Its control path, however, still enters the kernel on each I/O: each cuFile call traverses the filesystem stack (VFS and the underlying filesystem), the block layer, and the kernel NVMe driver, where the nvidia-fs module intercepts each request’s DMA mapping and translates every 4-KiB shadow page into its cached GPU bus address [18]. Large transfers amortize this fixed per-I/O cost; for small, latency-sensitive requests prevalent in KV-cache offloading and index lookups, it becomes the dominant cost. We present uGDS1, an open-source user-space GPU Direct Stor- age library built on four principles: user-space control, a unified ab- straction across GPU vendors, flexible workload-aware scheduling, and performance and debuggability that both follow from keep- ing I/O in user space. The host CPU constructs NVMe commands, manages hardware queues, and handles completions entirely in user space, while payloads move directly between SSDs and GPU memory through PCIe peer-to-peer DMA. A lightweight kernel helper (ugds_drv.ko) is used only for one-time privileged setup. Keeping I/O initiation on the CPU matches how GPU applications already manage data movement and consumes no GPU compute. uGDS partitions hardware queues between synchronous and batch traffic, tracks in-flight DMA so that no buffer is released while the SSD may still access it, and exposes cuFile-style synchronous, batched, and stream-ordered asynchronous APIs with polling or interrupt-driven completion on both NVIDIA CUDA and AMD HIP. Our roadmap focuses on three directions. NVMe-oF and Multi-SSD Support. Each uGDS handle currently drives a single local PCIe SSD. A Lightweight Built-In Scheduler. Synchronous requests are cur- rently dispatched round-robin across QPs, and each request holds its QP until its final completion (Section 2.5). This keeps the fast path simple, but it ignores queue occupancy, and a large request can delay small requests that land on the same QP. We plan to add a simple scheduler between the API and the hardware queues. It will track outstanding work per QP, place each request on the least- loaded queue, split large requests into chunks that can interleave with small ones, and bound per-queue depth. It will also support ordering-aware stream batches: a group of requests is ordered as a whole with respect to its stream, while requests inside the group carry no mutual order and can be issued concurrently on a deep queue and completed out of order. This matches workloads such as KV-cache restoration, which need ordering only between a batch of reads and the kernel that consumes them, without forcing ap- plications to fan I/O out across streams. Conclusion and Outlook

This paper presented uGDS, an open-source user-space GPU Direct Storage library. uGDS keeps the entire NVMe command lifecycle in user space and limits the kernel to one-time privileged setup; it normalizes CUDA and HIP memory into one controller-visible abstraction; and because it owns the hardware queues, it partitions them by traffic class and selects the completion policy per I/O mode. The result is a clean division of responsibilities: the CPU orchestrates, the SSD transfers, and the GPU computes. Our results show that CPU-initiated GPU direct I/O, carefully engineered on a multicore host, captures the user-space benefit without consuming GPU compute or changing how applications manage data. uGDS reduces small-request latency by up to 84.1%, outperforms GDS in Wei et al. little to the per-request cost that the current design minimizes.
