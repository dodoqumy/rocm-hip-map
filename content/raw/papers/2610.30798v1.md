## 摘要

Large language models (LLMs) achieve high inference efficiency using optimized GPU kernels generated by just-in-time (JIT) compilation frameworks such as Triton. Triton compiles GPU kernels through an MLIR/LLVM-based pipeline. We investigate whether a Rowhammer-induced bit-flip in the CPU's DRAM can degrade GPU-based LLM inference performance while preserving output correctness. We present LLVMhammer, the first Rowhammer attack that causes LLM inference slowdown by inducing a bit-flip in Triton's compilation pipeline. A bit-flip in a performance-critical optimization pass causes Triton to generate a functionally identical but suboptimal GPU kernel. Since Triton caches the generated kernel on disk, a single successful bit-flip causes persistent slowdown across subsequent inference executions. Triton's target-independent stages are shared across GPU vendors, which makes our attack GPU vendor-agnostic. To identify exploitable bit-flip locations without manual inspection, we build Karnage, a tool that isolates useful bit-flip locations in Triton's target-independent compilation pipeline. We evaluate LLVMHammer across a diverse set of LLMs, including Qwen2.5-7B-Instruct, Llama-3.1-8B-Instruct, Mistral-7B-Instruct-v0.3, and Deepseek-llm-7B-chat, across NVIDIA RTX 4090 and AMD RX 7900 XTX GPUs. LLVMhammer increases inference latency of an LLM inference server running on a single GPU by 4-16\%, which, in turn, can translate into additional annual operating costs at the scale of multi-GPU deployments. We further show that LLVMhammer can also corrupt LLM outputs across different GPU vendors, reducing BERTScore to as low as 25\%, illustrating the broader security implications of bit-flips in Triton's compilation pipeline.

## I. INTRODUCTION

Large language models (LLMs) have become ubiquitous across a wide range of applications, from conversational AI and code generation [1] to document summarization [2]. The demand for LLM-powered services continues to grow rapidly [3]. The effectiveness of an LLM deployment depends on both output correctness and inference efficiency. Correct- ness determines whether the model produces accurate and reliable responses. Inference efficiency is determined by how effectively the deployment utilizes its computational resources and consequently, the throughput it can achieve, measured in terms of the number of tokens generated per second and the number of requests served per second. Lower inference efficiency reduces throughput and increases operational costs. Modern LLMs achieve high inference efficiency by executing optimized GPU kernels for matrix multiplication and attention computations. When a DRAM row is activated sufficiently many times within a single refresh interval (typically 64 ms in DDR3 and DDR4 DRAMs and 32ms in DDR5 DRAMs), the affected neighboring cells may lose sufficient charge that, upon subsequent access, the sense amplifier misreads their stored value, resulting in a bit-flip. To mount a successful Rowhammer attack, an attacker must follow three key steps [40], as shown in Fig. 3. The attack begins with memory profiling ( 1 ), in which the attacker profiles the DRAM to identify DRAM locations susceptible to bit-flips by allocating memory chunks from their own address space. It identifies the page-frames (fixed-sized blocks in DRAM that hold an OS page) that have bit-flips at offsets suitable for their purpose. Upon finding suitable bit- flip locations (i.e., at desired offsets within a DRAM page frame), the attacker manipulates the victim process’s memory allocation so that the sensitive victim data or code is mapped to these locations. Typically, the OS’s page-frame allocation policy, which allocates page frames without respecting process boundaries, is exploited in this step. This process is known as memory massaging ( 2 ) [47], [48], [41], [8], [17]. Finally, during the hammering phase ( 3 ), the attacker repeatedly accesses the identified aggressor rows in its own address space to induce bit-flips in the victim’s rows. LLVM [24] provides a widely used intermediate represen- tation called LLVM IR. LLVM optimizes programs using a sequence of optimization passes. Each pass analyzes or trans- forms the LLVM IR. These passes reduce register pressure or instruction count. Most LLVM passes are target-independent. LLVM passes do not depend on the target instruction set. The same optimized IR supports many target instruction sets. Examples include x86, ARM, AMDGPU, NVPTX, and RISC- V. Only the final code generation depends on the target. MLIR [23] extends this idea with multiple intermediate representations. These representations are called dialects. Each dialect defines its own operations and types. Multiple dialects coexist within a single compilation pipeline. The compiler gradually compiles programs across these dialects. Subsequent stages produce LLVM IR or target-specific representations. MLIR optimization passes work on specific dialects. Each pass only understands its own dialect and ignores lower target- specific dialects. Therefore, the same optimizations work across different target backends. The boundary between ( 2 ) and ( 3 ) is the critical archi- tectural divide for this work. Every optimization pass that operates at ( 1 ) or ( 2 ) on Triton IR or Triton-GPU IR is target-independent by construction: it operates on abstractions that carry no knowledge of the target backends like NVIDIA or AMD, and its output feeds into all the vendor backends equally. A bit-flip in a data structure that one of these passes reads or writes is therefore not a bit-flip against a single ven- dor’s compiled artifact; it is a bit-flip against a representation that every vendor’s backend subsequently consumes. Every pass that operates at ( 3 ) or ( 4 ), in contrast, operates on a vendor-specific representation, and a bit-flip there affects only the backend whose IR it corrupts. C. Triton and its compilation pipeline Triton [20] is an open-source compiler and Python-based domain-specific language (DSL) that lets developers write GPU kernels without expertise in low-level GPU programming models such as Compute Unified Device Architecture (CUDA) or Heterogeneous-computing Interface for Portability (HIP). Triton’s compiler is responsible for architecture-specific op- timizations such as register allocation, shared-memory place- ment, vectorization, and instruction selection. This design has driven Triton’s rapid adoption as the kernel compiler for attention and matrix-multiplication kernels in LLMs’ infer- ence [19]. D. vLLM vLLM [19] is an open-source inference serving framework designed to run LLMs efficiently. It uses PagedAttention [19] to divide the key-value (KV) cache into fixed-size memory blocks. This design improves GPU memory utilization, re- duces fragmentation, and enables efficient sharing of the KV cache across concurrent requests, allowing vLLM to achieve high inference throughput. To execute LLM inference, vLLM uses Triton to generate optimized GPU kernels for attention, matrix multiplication, and elementwise operations such as activation functions and layer normalization. Triton compiles these kernels through the MLIR/LLVM compilation pipeline at inference startup and stores the compiled binaries for later reuse. Threat model Victim. The victim runs an LLM inference service on a shared physical host [8], [17], [16], and uses Triton as the GPU kernel compiler for GPU inference. The victim’s model weights are inaccessible to co-tenant processes. We consider the victim’s model trustworthy: its weights are free from prior poisoning or trojan attacks [8], [17], [16], and the Triton source and MLIR/LLVM toolchain the victim uses are unmodified and obtained from trusted providers. Attacker. The attacker is a malicious co-tenant on the same physical host as the victim, consistent with the cloud co- tenancy threat model established by prior Rowhammer attacks on ML systems [9], [8], [17], [10]. The attacker has the following capabilities: (i) it runs an unprivileged user-space CPU process on the same physical machine as the victim and has no direct read or write access to the victim’s process memory, model weights, or the Triton/MLIR/LLVM source, (ii) the attacker can allocate physical DRAM pages and perform Rowhammer to induce bit-flips in physically adjacent DRAM rows, following the standard Rowhammer attack [4], [49], [50], [46], [42], [43], and (iii) the attacker cannot modify the Triton source, the MLIR/LLVM toolchain, the victim’s model weights, or the victim’s inference serving configuration. At the LLVM IR level, the bit-flip causes the compiler to emit four separate scalar inline-asm calls in place of a single vectorized call, replacing one ld.global.v4.b32 instruction that loads four 32-bit values in a single transaction with four individual ld.global.b32 instructions that each load one value. This change propagates directly into the PTX: the baseline emits 128-bit coalesced loads and stores using ld.global.v4.b32 and st.global.v4.b32, while the flipped kernel emits one scalar 32-bit instruction per value, producing four times as many memory transactions for the same amount of data. At the SASS level the consequence is most stark: the six 128-bit vectorized global memory transactions (LDG.E.128 and STG.E.128) in the baseline are absent in the flipped kernel, replaced by 48 half-width 16-bit scalar loads (LDG.E.U16) that did not exist in the baseline.

LLVMhammer countermeasures. LLVMhammer relies on two properties of the Triton compilation pipeline: the persis- tence of the compiled kernel artifacts in the on-disk cache and the integrity of the libtriton.so binary in memory. Early research demonstrated that Rowhammer enables OS privilege escalation [80]. Subsequent work extended these attacks to cross-virtual-machine attacks, such as Flip Feng Shui [40], kernel-manipulation attacks, such as Go Go Gad- get [81], and hypervisor attacks, such as HyperHammer [82]. A recent large-scale, fully automated study [83] across 822 systems has shown that Rowhammer remains pervasive across a broad range of real-world, consumer-grade systems. Re- searchers have also expanded Rowhammer trigger mechanisms beyond traditional CPU-based exploitation. These mechanisms include integrated GPUs that induce bit-flips in shared CPU DRAM [84], remote network-based attacks using Network Interface Cards [85], FPGA-based attacks [86], browser-based attacks [87], [47], and ARM/Android platforms [88]. Targeted software defenses such as SoftTRR [69] and CATT [70] protect specific privileged CPU data structures such as page tables and kernel memory, preventing privilege escalation, but do not prevent bit-flips in unprotected DRAM regions. Guard-row approaches like ZebRAM [71] alternate guard and data rows to absorb bit-flips but incur a 50-67% DRAM capacity overhead, making them impractical. Coarse- grained isolation schemes like Siloz [72] assign entire DRAM subarrays to individual domains but limit the number of sup- ported domains and introduce severe memory stranding. The more recent Citadel [73] addresses many of these scalability limitations by supporting thousands of variably-sized domains, yet still does not protect against shared-library-based attacks. Memory Band-Aid [74] instead throttles per-bank DRAM bandwidth in the memory controller to keep row activations below the Rowhammer threshold, but current hardware lacks per-bank limits, forcing a global throttle that incurs overheads of up to 431%. MOAT [75] further shows that Panopticon [76], which inspired JEDEC’s PRAC+ABO framework in DDR5, is vulnerable, indicating that PRAC-based mitigations are not inherently secure. Rowhammer remains an unsolved problem as existing mitigations continue to be circumvented [46], [45]. GPUHammer [16], GDDRHammer [89] and GeForge [90] further demonstrate Rowhammer attacks against GDDR6 memory used by GPUs, while PRowhammer [17] shows that CPU-side Rowhammer can corrupt GPU workloads through bit-flips in host DRAM. GPUBreach [18] demonstrated a Rowhammer-based GPU privilege-escalation attack via page- table tampering, using the resulting arbitrary GPU read/write primitive to leak cryptographic keys, stealthily corrupt ML model code, and even escalate to root privileges on the host CPU despite IOMMU protection. Rowhammer vulnerabilities also persist across successive DRAM generations, with attacks demonstrated on DDR3 [4], [80], [40], [91] and DDR4 even in the presence of the TRR mitigation [43], [42], [92], [93], [94], LPDDR4 [42], and DDR5 [45], [46]. Experimental results further show that ECC-protected DRAM remains vulnerable to targeted bit-flips despite on-die mitigation mechanisms [49], [50], [46], [95].

## VIII. CONCLUSION

In this work, we investigated whether a Rowhammer- induced bit-flip could reduce LLM inference efficiency without affecting output correctness. We presented LLVMhammer, the first Rowhammer attack that caused LLM inference slowdown by inducing a bit-flip in Triton’s target-independent com- pilation pipeline. A single bit-flip in a performance-critical optimization pass caused Triton to generate a correct but suboptimal GPU kernel. Since Triton cached the generated kernel on disk, the slowdown persisted across inference ses- sions and process restarts without any output anomaly to prompt investigation. We built Karnage, a tool that identifies exploitable bit-flip locations in Triton’s target-independent pipeline without manual inspection, turning a one-off finding into a repeatable methodology. As Triton’s target-independent stages are shared across GPU vendors, bit-flip locations iden- tified once transferred across NVIDIA and AMD GPUs. We evaluated LLVMhammer on four LLMs across NVIDIA RTX 4090 and AMD RX 7900 XTX GPUs. LLVMhammer in- creased inference latency by 4-16%. We further demonstrated that the same attack target corrupted LLM outputs, reducing BERTScore to as low as 25%.
