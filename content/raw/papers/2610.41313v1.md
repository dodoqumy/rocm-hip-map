## 摘要

Migrating from Fortran to C++/Kokkos broadens access to hardware accelerators through backends such as CUDA and HIP while offering greater flexibility in software design. However, legacy Fortran applications often have large codebases, making manual porting time-consuming and costly. Recent advances in large language models (LLMs) and AI coding agents have made large-scale code migration increasingly feasible. In this study, we ported NICAM (Nonhydrostatic ICosahedral Atmospheric Model), a legacy Fortran climate model accelerated with OpenACC, to C++/Kokkos with the assistance of Claude Code. The agent translated the code directly from Fortran to C++/Kokkos under human review. Approximately 140,000 lines of Fortran were analyzed and ported into 35,000 lines of C++/Kokkos, covering the dynamical core and seven physics packages. A 100-member ensemble comparison with the original Fortran model showed that the port is statistically consistent with the original. Performance was evaluated on Miyabi-G, an NVIDIA GH200 cluster, and Sirius, an AMD MI300A cluster. Compared with the Fortran/OpenACC baseline on GH200, the port achieved application speedups of $1.71\times$ on GH200 and $1.54\times$ on MI300A. The CUDA build achieved a GPU kernel-time speedup of $1.38\times$ on GH200. After normalization by peak memory bandwidth, the HIP build on MI300A achieved $0.96\times$ the kernel performance of the Fortran/OpenACC baseline.

## 1
Introduction

High-performance computing (HPC) systems span a diverse range of processor and accelerator architectures, with different requirements for parallel execution and memory access. Scientific applications must adapt to this diversity while remaining maintainable over development lifetimes that often outlast individual hardware generations. Performance portability is therefore an important goal. A shared implementation should run efficiently across target architectures without requiring a separate application codebase for each platform. Kokkos addresses this goal through C++ abstractions for parallel execution, memory spaces, and multidimensional data layouts [9]. Its CUDA and HIP backends provide a route to NVIDIA and AMD GPUs from a common source codebase [22]. Adopting such a framework is a substantial undertaking for mature scientific applications because many have accumulated large Fortran codebases over decades. These codebases combine numerical algorithms, physical param- eterizations, communication routines, and input/output infrastructure. Migrating these applications to C++/Kokkos requires both language translation and careful mapping of data structures and parallel execution while preserving numerical behavior. The HOMMEXX atmospheric dynamical core illustrates the feasibility of this approach and the verification and performance engineering involved [3]. The expertise and time required for manual migration remain a barrier to porting a complete application. Recent advances in large language models (LLMs) and coding agents offer a way to assist this work. With access to development tools, these agents can combine source-code translation with compilation, testing, and iterative correction. Fortran-to-Kokkos studies have demonstrated this approach on scientific kernels [12]. Together, these studies demonstrate the potential of coding agents for scientific software migration. For a production atmospheric model, the resulting implementation must preserve the behavior of coupled dynamical and physical processes while executing efficiently across target architectures. We therefore investigate whether human-directed, agent-assisted migration can meet these requirements in an application-scale C++/Kokkos port. We address this question using the Nonhydrostatic ICosahedral Atmospheric Model (NICAM), whose original dynamical framework was developed by Tomita and Satoh [21]. NICAM uses an icosahedral grid and nonhydrostatic equations to support global atmospheric simulations. At sufficiently fine resolution, it explicitly represents deep convective circulations [20]. Its development over more than two decades has included substantial adaptation to successive supercomputers. Yashiro et al. applied OpenACC to its dynamical core on TSUBAME2.5 [23], and subsequent work demonstrated large-scale NICAM-based ensemble data assimilation on Fugaku [24]. Building on these efforts, we aim to make a production configuration of NICAM available on both NVIDIA and AMD GPUs through C++/Kokkos. The C++ implementation also provides a basis for future tuning through Kokkos and, where needed, native CUDA or HIP interfaces. In this study, we use Claude Code [1], primarily with the Fable 5 model, to translate NICAM directly from Fortran to C++/Kokkos under human direction. The human defines the scope and constraints, reviews plans and structural decisions, and assesses progress at defined checkpoints. The migration proceeds module by module, using the Fortran implementation as the numerical reference and retaining its organization to support comparison and maintenance. Our scope covers the dynamical core and seven physics packages used in the selected production configuration. Component- level checks support development, while ensemble consistency testing evaluates the completed port outside the agent loop. This paper makes three contributions. • An application-scale port of NICAM’s selected production configuration, translating approximately 140,000 lines of Fortran into about 35,000 lines of C++/Kokkos model source and covering the dynamical core and seven physics packages. • A layered validation approach combining component-level reference comparisons and an ensemble-inspired consistency test for coupled atmospheric simulations. • An experimental evaluation of performance on Miyabi-G (NVIDIA GH200) and Sirius (AMD MI300A), together with comparisons of 100-member ensembles from each implementation to assess agreement in simulated means and variability. The remainder of this paper is organized as follows. Section 2 reviews related work on performance-portable scientific applications, agent-assisted code migration, and ensemble consistency testing. Section 3 presents our workflow, porting strategies, and verification protocol. Section 4 reports correctness, performance, and cost results and discusses their limitations. Section 5 concludes the paper and outlines future work.

## 2
Related Work

Modernizing weather and climate models for heterogeneous hardware predates LLM-based code generation. Kokkos abstracts parallel execution and data layout across architectures [9, 22], enabling applications such as LAMMPS to target multicore CPUs and GPUs [17]. SCREAM uses C++/Kokkos for a global atmosphere model designed for cloud-resolving simulations [8]. Its dynamical core, HOMMEXX, is a C++/Kokkos port of a Fortran atmospheric dynamical core that Migrating a Legacy Scientific Application with an AI Coding Agent: NICAM from Fortran to Kokkos 3 preserves the underlying numerical formulation [3]. These efforts demonstrate both the feasibility of application-scale performance portability and the engineering effort it requires. Compiler directives and domain-specific languages offer additional routes. Earlier NICAM work accelerated its Fortran dynamical core with OpenACC [23]. CLAW generates OpenACC or OpenMP code for Fortran physical parameterizations from a single-column abstraction [6]. Pace expresses the FV3 dynamical core and GFDL cloud microphysics in Python and uses GT4Py for architecture-specific code generation [7]. These approaches delegate hardware adaptation to compilers and code generators, whereas agent-assisted migration helps construct the translated application, with Kokkos providing portability. Early studies of LLMs for HPC focused on the quality of generated kernels and the effects of prompting. Godoy et al. evaluated OpenAI Codex on numerical kernels across several parallel programming models, including Kokkos, and found that the generated code depended on both the programming model and the prompt [11]. Nichols et al. introduced ParEval to evaluate generated parallel code across scientific computing tasks, using metrics that consider correctness and execution performance [18]. Such studies provide controlled settings for examining model capabilities, but successful kernel generation alone does not establish the correctness of a coupled scientific application. Subsequent work incorporated compiler and execution feedback into iterative translation. Fortran2CPP uses a dual-agent process to generate translation dialogues covering compilation, execution, unit testing, and error correction. It then uses these dialogues to train translation models [5]. Gupta et al. present a multi-agent workflow for translating Fortran kernels to Kokkos, with separate roles for translation, compilation, testing, debugging, and optimization [12]. These studies demonstrate how automated feedback can be organized during migration, with evaluations focused mainly on individual programs or kernels. Recent studies have extended agent-assisted translation to larger scientific applications. Koldunov et al. report a port of the FESOM2 ocean model under expert supervision, first translating the Fortran core to C and then moving to C++/Kokkos [15]. Their validation includes comparisons with an intermediate C reference at the kernel and whole-model levels, together with comparisons against the original Fortran model in simulations lasting more than one model year. The intermediate implementation separates language translation from the introduction of Kokkos parallelism. Our NICAM port follows a direct Fortran-to-C++/Kokkos route and covers the dynamical core and seven physics packages of a production atmospheric configuration. Sadr et al. present ORB5X, a direct C++/Kokkos translation of the Fortran ORB5 gyrokinetic particle-in-cell code [19]. Their workflow combines incremental translation, preservation of source structure, developer review, and numerical checks. Verification includes unit tests and comparisons of diagnostic fields from complete plasma simulations, and performance is evaluated on NVIDIA and AMD systems. Our independently developed NICAM workflow shares these general practices. The distinction in this study lies in the atmospheric application and its validation through component-level reference comparisons and ensemble statistics. Ensemble testing has an established role in assessing changes to weather and climate software when bitwise agreement is unavailable. Baker et al. introduced the CESM ensemble consistency test, which evaluates new simulations against the variability represented by an accepted reference ensemble [2]. Milroy et al. developed an ultra-fast variant using only nine model time steps [16]. Zeman and Schär describe a methodology that compares ensembles from different model executables to detect changes in their statistical behavior [25]. These studies motivate assessing a translated atmospheric model using the variability of perturbed simulations in addition to checking individual routines. ## 3
Coding Agent Workflow

3.1 Overview Figure 1 summarizes the human-directed workflow used to port NICAM from Fortran to C++/Kokkos. The human first defines the migration goals, requirements, and constraints. In plan mode, the coding agent examines the Fortran source, clarifies the scope with the human, and proposes a porting plan with incremental milestones. Development begins after the human approves the plan and proceeds one module or physics package at a time. Within each milestone, the agent investigates the relevant routines and translates them directly into C++/Kokkos under the agreed constraints. The agent then builds and tests the new implementation using component-level comparisons against the Fortran reference. These tests execute the translated routines using inputs dumped from the Fortran model and compare their outputs with the corresponding reference dumps. Once these checks pass, the agent rebuilds and runs the accumulated unit-test suite to detect regressions in previously implemented components. A failure in either testing stage returns the workflow to development, where the agent revises the implementation and repeats the tests. After both testing stages pass, the human reviews the test results and key structural decisions, including source organization and routine call order. Short model runs of 30 or 60 time steps are also compared with the Fortran reference to check the integration of the new component. If the human identifies a problem or requests further changes, the workflow returns to development. Otherwise, the milestone is approved, progress is recorded, and the loop advances to the next module or physics package. This process continues until all components in the selected configuration have been ported and approved. Longer simulations and ensemble consistency testing subsequently assess the completed port outside the agent loop. Human direction began with a concise kickoff document that specified the migration objective, immediate tasks, and operational constraints. The document is reproduced in Appendix A. The overall objective was to port NICAM from Fortran to C++/Kokkos, while the immediate task was to agree on a plan and develop a minimal executable version. The instructions identified the local development environment, required the code to be built and run in Docker, and highlighted the original model’s big-endian input/output. They also required YAML configuration in place of Fortran namelists and set rules for file access, software installation, and GPU job execution. The detailed breakdown of the port was left to the planning stage. In Claude Code’s plan mode, the agent examined the Fortran source and asked the human to resolve three planning choices. First, we defined the initial executable as the dry dynamical core with physics disabled. Second, we selected a standalone C++/Kokkos implementation to keep the target codebase self-contained and maintainable, rather than incrementally replacing routines within a mixed Fortran/C++ executable. Third, we selected the single-header version of fkYAML for configuration parsing [10]. These decisions established the initial scope, implementation strategy, and choice of configuration library before development began. The agent recorded the agreed plan in Porting_Progress.md. The plan organized the dry dynamical core port into milestones that progressed from the build system and supporting modules to numerical operators, model state arrays, and the time-stepping driver. A module map linked Fortran sources to proposed C++ files and reference checks, while milestone descriptions specified the planned work and completion criteria. The document also included a preliminary roadmap for adding physics packages after the dry core and a log of decisions confirmed by the human. The plan was subsequently refined as implementation and verification progressed. 3.3 Mapping and Porting Fortran modules were mapped to C++ classes, with NICAM classes and functions organized within the nicam namespace. The classes own model state arrays through Kokkos Views, and their instances are scoped so that the Views are destroyed before Kokkos::finalize(). This makes data ownership and lifetime explicit. Before launching a device kernel, member Views are copied into local handles that KOKKOS_LAMBDA captures by value. These shallow copies refer to the same allocations and allow the kernel to access the required arrays without capturing a pointer to the host-side owning object [14]. The same organization supports isolated testing. A unit test can construct only the objects required by a routine, populate them with dumped reference inputs, and execute the translated routine. Separate object instances also allow multiple configurations to coexist without repeatedly resetting module-level global state. Dependencies that were implicit in Fortran use statements become explicit in C++ interfaces. For example, Grd::setup requires an Adm object, making the grid’s dependency on the model topology visible to both the caller and the compiler. Because individual NICAM modules can be large, the agent maintained working notes that mapped variables, routines, and code sections between the two implementations and recorded their callers and consumers. These notes supported incremental translation and human review, although they did not constitute a formal dependency analysis. Migrating a Legacy Scientific Application with an AI Coding Agent: NICAM from Fortran to Kokkos 7 Tier 1. Component-level reference tests. The tests used data from the Fortran simulations, including the atmo- spheric state and boundary conditions. Before translating a routine, we dumped its inputs and outputs from the Fortran implementation into binary files. The corresponding unit test supplied the same inputs to the C++/Kokkos routine and compared its outputs with the reference dumps. The standard acceptance threshold was a relative error of at most 10−13 or an absolute error of at most 10−12, with many comparisons agreeing at approximately 10−15. Exceptions for ill-conditioned intermediate quantities were documented, and their downstream consumers were checked under strict tolerances. These tests exercised individual routine calls from a reference step, providing rapid feedback on translation errors without requiring a long model integration. The accumulated test suite was rerun after each milestone to detect regressions. Tier 2. Human-reviewed short integration runs. At each milestone, we compared model fields and energy and mass budget diagnostics from runs of 30 or 60 time steps with the Fortran reference. This stage checked initialization, coupling, and repeated execution for errors that isolated routine tests could miss. For example, after the physics packages had passed their unit tests, an integrated run revealed a systematic discrepancy in surface downward longwave radiation. The routine tests supplied the surface temperature directly from reference dumps, whereas the coupled model had to reconstruct it during surface initialization. The corresponding reconstruction was missing from the port, so the unit tests did not expose the error. The budget discrepancy prompted inspection and correction of the initialization path. Human structural review complemented these numerical checks, particularly for dependencies and routine call order. Tier 3. Ensemble-inspired consistency testing. Atmospheric simulations amplify small numerical perturbations through chaotic dynamics, so agreement between individual trajectories becomes difficult to interpret as the integration proceeds. The migration from Fortran/OpenACC to C++/Kokkos also changes the compiler and parallel programming model, which can alter the order of floating-point operations in reductions and make the resulting numerical differences harder to interpret. We therefore assessed the completed port using an ensemble approach inspired by CESM-ECT [2]. Our test compares diagnostic quantities and their distributions directly using 𝑧-scores, without implementing the principal-component-based acceptance procedure of CESM-ECT. We generated the ensemble members by adding independent uniform temperature perturbations in [−10−10, 10−10] K to the initial state and used the same perturbed states for both implementations. Evaluation

4.1 Experimental Environment We evaluated the port on two supercomputers with different accelerator architectures. Miyabi-G uses NVIDIA GH200 Grace Hopper Superchips and is operated by the University of Tokyo and the University of Tsukuba [13]. Sirius uses AMD Instinct MI300A APUs and is operated by the Center for Computational Sciences at the University of Tsukuba [4]. Table 1 summarizes the hardware, software, and principal build options. On both systems, the port uses Kokkos 5.1.1 and C++20 in Release builds, with the CUDA backend on Miyabi-G and the HIP backend on Sirius. The Fortran/OpenACC reference was evaluated on Miyabi-G. We used three grid configurations, all with 78 vertical layers. The gl07rl00Az78 configuration has approximately 56 km horizontal spacing and 10 regions. It was used during development, for the single-accelerator performance breakdown, and for the ensemble test. For strong scaling, gl07rl01Az78 retains the same horizontal resolution but partitions the domain into 40 regions. The finer gl09rl03Az78 configuration has approximately 14 km spacing and 640 regions. We believe the porting process went smoothly not only because of the capabilities of the LLM and coding agent but also because of NICAM’s consistent data structures. Most model data are stored in arrays organized as (ij, k, g, l). The Fortran source is well maintained and clearly structured, and its OpenACC and OpenMP directives provided useful guidance for the coding agent. In our experience, the size of the codebase posed a greater challenge for human review than for the agent’s translation work. The three verification tiers provide complementary evidence of consistency with the Fortran reference for the tested configuration. The surface-temperature initialization error illustrates why human review and integrated model runs remain necessary even after component-level tests pass. Supplying a routine with reference inputs can bypass errors in Migrating a Legacy Scientific Application with an AI Coding Agent: NICAM from Fortran to Kokkos 15 the code that produces those inputs during a coupled simulation. The current unit tests also use a limited set of dumped inputs and do not systematically cover boundary cases. A broader collection of reference inputs is therefore needed to improve test coverage. The performance results show that there is still room for architecture-specific tuning of the shared implementation. Both Kokkos builds outperform the Fortran/OpenACC reference on GH200, although the MI300A run is slower than the GH200 run despite its higher peak memory bandwidth and FP64 throughput. Using peak memory bandwidths of 5.3 TB/s for MI300A and 4.02 TB/s for GH200, the bandwidth-normalized kernel performance of the HIP build is approximately 96% of that of the Fortran/OpenACC reference. The HIP build currently retains the CUDA tile sizes, so tuning the execution policy for MI300A is one direction for further work. Further profiling is needed to assess whether multidimensional index calculations, remaining conditional branches, or implementation choices made for readability contribute to the performance gap. Because this was our first application-scale port with a coding agent, we frequently audited progress and requested confirmation before continuing. In retrospect, we believe some of these exchanges could have been avoided. The instruction counts therefore reflect both the work required for the port and our cautious approach to directing the agent. Human review and the subscription’s five-hour usage limits were the main constraints on progress. The agent could generate code faster than the human could inspect it, so reviewing numerical logic and integration details took substantial time. Token consumption was also difficult to predict for individual milestones, and development was repeatedly interrupted when the usage limit was reached. Interruptions during implementation raised concerns about whether the agent could resume with sufficient context. The completed port demonstrates the feasibility of agent-assisted modernization, with progress shaped by the human’s capacity to review and verify the generated code.

## 5
Conclusion

We ported a production configuration of NICAM directly from Fortran/OpenACC to C++/Kokkos using Claude Code under human direction. The port covers the dynamical core and seven physics packages, translating approximately 140,000 lines of Fortran into 35,000 lines of C++/Kokkos model source. Validation combined component-level reference comparisons, short integration checks, and an ensemble-inspired consistency test. Two 100-member ensembles provided evidence of consistency with the Fortran reference across 59 evaluated quantities over 10-day simulations. Compared with the Fortran/OpenACC baseline on GH200, the port achieved application speedups of 1.71× on GH200 and 1.54× on MI300A. The corresponding GPU kernel-time speedups were 1.38× and 1.27× through the CUDA and HIP backends, respectively. After normalization by peak memory bandwidth, the HIP build reached 96% of the Fortran baseline’s kernel performance. The overall recorded token usage corresponds to an estimated API list-price cost of USD 5,589. These results demonstrate the feasibility of agent-assisted modernization at application scale with human direction and layered verification. Future work will extend the port to additional NICAM components and broaden the reference inputs used in unit tests. We also plan to use the development and verification procedures from this port to build reusable agent skills and a more automated workflow. We are preparing a second porting exercise using the dry dynamical core of the current NICAM version to evaluate this workflow. 16 Ren et al.
