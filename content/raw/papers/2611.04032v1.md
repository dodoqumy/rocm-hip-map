## Abstract

Serving a large language model (LLM) efficiently requires making several key decisions: the serving engine, how the model is split across graphics processing units (GPUs), numeric precisions, scheduler settings, speculative decoding, key–value (KV) cache management, and prefill–decode disaggregation. The best configuration depends on the model, hardware, workload, and serving objective (interactivity, time to first token, or throughput). Today, operators typically rely on trial and error to identify the best combination, with each experiment occupying one or more nodes for several minutes. Exhaustively evaluating all candidate configurations in our study would require approximately 25,000 GPU-hours. We propose ROCm InferaSim, a framework that predicts LLM serving performance using a few short measurements. Many configuration choices, such as batch size, prompt length, and GPU count, change the amount of work performed by each GPU without changing the underlying GPU kernels. ROCm InferaSim benchmarks each distinct set of kernels once, on at most one node, and we call this measurement an anchor. Analytical laws carry the anchor to other deployments (a configuration on a given set of GPUs) that run the same kernels. For deployments spanning multiple nodes, ROCm InferaSim first reduces the configuration to a single-node equivalent, measures its performance, and then analytically scales the results to the full deployment. A simulator replays realistic multi-turn serving traffic, while an automated tuning agent uses the predicted performance to search for efficient serving configurations. We evaluate on AMD Instinct™MI355X GPUs with three engines (vLLM, SGLang, and ATOM). Measuring 11 anchors took 9.1 GPU-hours; measuring the 226 fixed-length configurations they cover took 204 GPU-hours. On 172 configurations that pass our measurement filters, time per output token has 8.1% median error. On a multi-turn coding workload, predictions are within 8% on throughput. For 159 additional deployments that run prefill and decode on separate GPUs, throughput is within 5.5%, although no such deployment is used as an anchor. Using predictions alone, among configurations an anchor covers, a short list of the mix planner’s five best candidates contains a deployment within 12% of the best feasible pairings of model and latency target.

ROCm InferaSim embeds its step model in a discrete-event simulator that captures queueing, batching and prefix reuse. A tuning agent and mix planner then search these predictions instead of evaluating every candidate on GPUs. Contributions. ## 2
Background

Engines and metrics. Serving engines process concurrent requests using continuous batching [57], adding and removing requests between steps as they arrive and finish. Each step advances every running request by one token and can also process chunks of new prompts, up to a token budget [2, 4]. Processing a prompt is prefill, and generating output tokens is decode. The KV cache is stored in pages [26], and requests that share a prefix reuse its cached KV [60, 41]. Users see time to first token (TTFT), time per output token (TPOT, per request) or inter-token latency (ITL, the gap between consecutive tokens), and throughput. TPOT and ITL have similar means but different tails. TTFT depends mostly on how long a request waits. Agentic traffic. Unlike fixed-length benchmarks, which issue independent requests, coding agents generate multi-turn sessions. A turn’s prompt can reach hundreds of thousands of tokens, much of it a prefix processed during earlier turns. Agents also pause to “think” between turns, creating dependencies in request timing. Agentic workloads therefore combine prefix reuse with interdependent requests. We evaluate both fixed-length and agentic traffic.

The Pareto sweep enumerates the space for each model, and the agent searches spaces too large to enumerate (§4). 3.4 Discrete-event simulator (DES) Why simulate requests. SLOs are usually set on tail latency, and tails have their own causes. In one measured run with 64 clients, the 99.9th-percentile ITL was 1392 ms while the median was 21.7 ms, because each newly admitted prompt stalls all running decodes. A model of averages cannot show this. The DES simulates individual requests and produces latency distributions. What it simulates. The DES advances a virtual clock through request arrivals, admission, steps and completions, and the step cost model prices each step. It mimics the target engine’s scheduler (token budget, chunked prefill, mixed steps and, for ATOM, separate prefill-only steps), a paged KV cache, a block-level prefix cache that evicts like the engines do, and routing across replicas. The cache hit rate is a result of the simulation, not an input. This scheduler model and the harvester’s launch code are the only engine-specific parts of ROCm InferaSim. Like our measurements, it runs C clients that each send a new request when the previous one finishes, or open-loop arrivals. Agentic sessions. A session’s next turn is sent only after the previous turn finishes and its think time passes. Its prefix hit comes from a simulated cache replayed in the engine’s admission order (Appendix A.1). Host time. Central processing unit (CPU) work per request (tokenization, detokenization, preparing uncached prompts) overlaps the GPU and is added only to TTFT and end-to-end latency. It is fitted per engine from the anchor runs. TTFT is reported both from admission, as engine benchmarks do, and from arrival, as users see it. Scheduler settings. Configurations that differ only in a scheduler setting run the same kernels, and the anchor alone cannot tell them apart. ROCm InferaSim models their effect on scheduling in the DES instead. These are the cap on running requests, the chunked-prefill budget, the attention-DP split of requests, the largest captured batch, and the KV capacity a KV-cache precision gives. This separates configurations that would otherwise tie (§5.7). 3.5 KV offload engines A multi-turn trace reuses long prefixes, but GPU high-bandwidth memory (HBM) holds the KV cache of only the most recent sessions. Offload engines add a second, larger tier in host dynamic random-access memory (DRAM): SGLang’s HiCache, LMCache [34] (used by our ATOM runs), vLLM’s CPU offload connector and, for disaggregated SGLang, the unified memory and bandwidth pool (UMBP) of MoRI (Modular RDMA Interface) [7], a remote direct memory access (RDMA) library from AMD. Nearly two in five runs of our agentic data use one. Offloading changes which prompt tokens must be recomputed. It leaves the kernels alone and is transferable. The DES models it as a second cache level. Blocks evicted from HBM move to DRAM, and a DRAM hit is copied back before the request runs (Appendix B.6). 3.6 Speculative decoding without an anchor Speculative decoding lets a small drafter propose several tokens that the main model then checks in one step. The drafters we measure are the models’ own multi-token-prediction (MTP) heads [18]. An anchor measured with speculation already includes the drafter’s cost and acceptance. Otherwise ROCm InferaSim prices each drafter layer like a main-model layer of the same kind, and takes the number of accepted tokens at each draft depth from InferenceX [46], a public collection of measured serving runs, optionally adjusted per domain with SPEED-Bench [1]. ## 4
The Tuning Agent

A prediction takes under half a second and orders candidates well (§5.7), which makes it usable in place of trials inside a search. The ROCm InferaSim tuning agent searches the serving space this way (Figure 4, details in Appendix J), following a two-phase design from automated tuning of distributed training. A lever is one setting the agent may change, together with its allowed values. There are 36 levers, covering the choices of Table 4, such as parallel widths, disaggregation and its pools, precisions, kernel backends, graph capture, scheduler budgets, draft depth, communication algorithms and kernel fusions. The agent optimizes one of 24 predicted objectives, such as throughput, latency, tokens/s per user, capacity or cost. Two phases. First, a fixed seed planner changes one lever at a time from a safe baseline. Each gain then has a clear cause. Then an LLM loop, written in DSPy [23] in the style of ReAct [53], reads the latest 40 trials in the ledger (the trial log). It writes hypotheses and 5–8 partial configurations and evaluates them one at a time, combining levers the seeds change separately. Legality. A candidate that does not fit in 90% of HBM or misses a latency target is rejected outright, and the ledger records why. Since the LLM’s proposals go through the same checks and predictions as the seeds, it can waste trials but cannot return an illegal or unpriced configuration. For each (TP, PP, EP) shape, one anchor serves all scheduler and load trials. Where no anchor applies, the agent uses simulate mode, only for ranking. Kernel fusions. An engine build can fuse adjacent kernels into one. The agent offers six fusion patterns found in kernel traces (Table 21). Each is priced at 75–100% of its ideal saving, which is the launch cost of the removed kernels (Table 5) plus the intermediate data no longer written to and read back from memory. Every trial reports the legal fusions saving at least 2% of its decode step (Appendix J). 4.1 Mix planner An operator serving several models needs a deployment mix, with one configuration per model and user class. The mix planner uses four latency tiers (Table 15): realtime, interactive, responsive and bulk. Each tier sets a minimum per-user token rate (interactivity) and a maximum TTFT. The planner predicts every candidate on the agentic trace with the DES. A candidate qualifies if it meets the interactivity target and its predicted TTFT is at most half the limit, which covers the TTFT error we measure in §5.6. Among those within 5% of the best predicted throughput per GPU, it picks the one with most headroom. ROCm InferaSim: Cut LLM Serving Trial Costs and Deploy the Best Configuration

## 5
Evaluation

We first check the parts that no anchor contains, communication and pipelines across nodes (§5.2–§5.3). We then measure prediction error on fixed-length and agentic traffic (§5.4–§5.6), check whether predictions order candidates correctly (§5.7), and test Pareto frontiers, speculative decoding and disaggregated serving (§5.8–§5.10). Finally we evaluate the planner’s choices and its cost (§5.11). 5.1 Methodology Setup. All measurements use nodes of eight AMD Instinct MI355X GPUs (288 GB of HBM3E each, connected by AMD Infinity Fabric™links), with recent vLLM, SGLang and ATOM builds on ROCm™7 software and graph capture on. The models range from large MoE models (DeepSeek-V4-Pro and -Flash, GLM-5.2, Kimi-K3, MiniMax-M3, Qwen3.5) to smaller ones such as Qwen3-14B, gpt-oss-120b and Llama-3.1-8B [15, 17, 24, 52, 39, 19]. Agentic runs replay the AgentX trace (§5.6), and 1k/1k means 1024 prompt and 1024 output tokens. Table 9 (Appendix D) lists the sets. Metrics. For fixed-length traffic we report the median absolute percentage error of mean TTFT, mean TPOT and output throughput. Agentic metrics vary by two orders of magnitude. For them we report an error factor, the geometric mean of max(ˆy/y, y/ˆy) over runs, where ˆy is predicted and y measured. A factor of 1.00 is exact, and 1.10 means a typical 10% miss in either direction. We report accuracy for anchored mode, and ranking for both modes. When an anchor covers a run. An anchor covers a target if it has the same engine build and the same layout (TP may be narrower), and was measured within 4× of the target’s concurrency. A narrower anchor must be a full batch sweep. Transferable choices such as prompt length, the KV tier, draft depth and replicas do not affect coverage. Covered targets use anchored mode. The rest are still projected in anchored mode from the nearest anchor of the same model, but only to rank, and are marked as such. 5.2 Collective communication Communication outside the anchor’s own GPUs, such as wider TP and EP groups and every transfer that leaves the node, comes from a model. We measured ROCm Communication Collectives Library (RCCL) collectives from 8 KiB to 1 GiB and vLLM’s custom all-reduce from 4 KiB to 8 MiB, on 2–8 GPUs and across two nodes over AMD Pollara network cards. ## 6
Related Work

Profile-based serving simulators. Vidur [3] profiles each operator for every model and TP width, and supports only dense models, so it cannot run any MoE model we evaluate. We ported it to MI355X and ran it on the 30 SGLang Llama-3.1-8B runs of §C.1. Its median errors are 34%, 40% and 40% on TTFT, TPOT and throughput, against 14%, 7.2% and 7.4% for ROCm InferaSim. Vidur times its own FlashInfer [55] kernels and models no host or per-stage overhead. Operator-level simulators with MoE. APEX [31] searches DP, PP, TP and EP plans from profiled operators. LLMServingSim [11] co-simulates accelerators and serving software. AIConfigurator [51], the closest to ROCm InferaSim, composes aggregated and disaggregated step times from a per-GPU kernel database. Frontier [16] and KernelSight-LM [54] add disaggregation, graphs, speculation or roofline kernel models to operator-level simulators. All build a step operator by operator and re-collect their databases per model, engine build and kernel library. ROCm InferaSim instead measures the whole step, so graph padding, fused kernels and host time come with the anchor (Table 12). Analytical and hardware-design models. Roofline tools [58, 8], Optimus [25], LLMCompass [59], Calculon [22] and ASTRA-sim [44, 50] compute step times from hardware descriptions, and BestServe [20] ranks colocated and disaggregated strategies with per-stack efficiencies and no MoE. Like simulate mode they need no GPU, but they omit the fixed per-step cost that §3.1.2 keeps across widths. Tuning by trial. SCOOT [9] tunes vLLM and TensorRT-LLM flags with Bayesian optimization over live runs, and LLM-guided optimizers [33, 32] still pay for a real run per trial. ROCm InferaSim’s agent keeps the search loop [53, 23] but replaces each trial with a sub-second prediction. Prediction from measurements. Habitat [56], Daydream [62], Lumos [30] and hybrid measured-analytical models [43] predict training performance from measured kernels, traces or small benchmarks. Serving differs because the step also depends on traffic, through batching, prefix reuse, speculation [28] and disaggregation [40, 61], which now also separates attention from experts [63] and prefill across datacenters [42]. ## 7
Limitations

All measurements were taken on AMD Instinct MI355X GPUs. The method is not tied to this hardware: given short anchor runs of the same kernel sets on another GPU, the same transfer laws predict its other deployments. Extending the evaluation to NVIDIA GPUs is future work.

## 8
Conclusion

ROCm InferaSim predicts LLM serving performance from a few short measurements instead of a trial per configuration. It anchors each kernel set once, on at most one node, and carries the anchor to other deployments with transfer laws that keep the fixed per-step cost and scale only the work that more GPUs divide. Deployments larger than a node are reduced, measured and restored. A discrete-event simulator replays multi-turn agentic traffic, and a tuning agent and mix planner search with them. Eleven anchors measured in 9.1 GPU-hours predict fixed-length TPOT with 8.1% median error and agentic throughput within about 8%, and 159 additional disaggregated deployments within 5.5% with no disaggregated anchor. Its predicted Pareto frontiers keep 83% of the measured frontier configurations, and its five-candidate short list reaches a near-best deployment in the feasible slots. Measuring each kernel set once and deriving the rest turns serving configuration from a search over hardware into a search over predictions.

The DES takes either a synthetic workload or a trace. A synthetic workload gives prompt and output lengths (fixed or drawn from a range), an arrival process, and optionally a pool of shared prefixes whose popularity is uniform or Zipf-skewed. A trace follows the Mooncake format, as JSON lines or a JSON array. Each record has an arrival timestamp, input and output lengths, and hash ids, the ordered hashes of the prompt’s fixed-size token blocks. Optional fields add a think time, a session id, the request this turn waits on, and the requests it joins (a turn that waits for several sub-agent calls). A compact form lets a record reuse the first n blocks of an earlier record, so long agentic contexts are not repeated in the file. Hash blocks are 512 tokens in Mooncake’s traces and 64 in AgentX; the DES infers the size from the trace and counts cache capacity in these blocks. Prefix cache. Each replica owns a content-addressed block cache. A block’s hash covers its whole prefix, so a block also identifies its predecessor and the cache forms a tree, as in a radix cache. A request’s hit is the longest leading run of its blocks already resident; only the uncached suffix is prefilled. Its blocks are then inserted, and blocks beyond the capacity the memory model gives the KV pool are evicted. Eviction takes the least recently used (LRU) leaf: a block is never dropped while a resident block continues from it, so shared heads survive pressure and only divergent tails are reclaimed. This matters: on the AgentX trace at 256 clients against DeepSeek-V4’s 231,336-block pool, flat LRU turns the sweep over contexts into a cycle that evicts every block just before its reuse (0% hits), while leaf-first eviction gives 90.6%, against the trace’s published reuse of about 92%. With a host-memory tier, evicted blocks move one tier down instead of being dropped, and a hit found there makes the request wait for the load. Hits depend on the order requests reach the cache, so the cache is replayed in the order the engine admits them. Requests that fit in the KV pool run in arrival order. When a backlog builds up, the engine picks the waiting request with the longest resident prefix (SGLang’s default policy, which vLLM’s prefix-caching scheduler approximates), and the replay does the same over the backlog only. A session turn is not a candidate until the request it waits on has been served, so it cannot take the hit that request creates. Each client’s next turn refills that client’s slot, so the context it continues is the one just served. Routing. With several replicas, the router picks a replica for each request before its hit is resolved. Policies are least-loaded, a KV-aware cost that trades prefix overlap against load like a cluster router’s, prefix hashing that colocates requests sharing a leading block, round robin and random. Under disaggregation a request goes to a prefill replica (the one holding its prefix on traces), its KV is handed off on the transfer backend, and it decodes on the least-loaded decode replica. Timed simulation. Each replica then runs its own event loop over a virtual clock: arrivals, scheduler steps and completions. Closed-loop clients send their next request when the previous one finishes plus its think time; open-loop requests arrive at their timestamps. At each step the scheduler model fills the batch as the target engine does, within the running-request cap and token budget, with chunked prefill, mixed or prefill-only steps, and pages of KV per request. A request’s cached prefix counts as already computed. The step cost model (anchored or simulate mode) prices the step’s mix of prefill tokens and decode contexts, the clock advances by that time, and each running request emits a token. Host time per request is added to TTFT and end-to-end latency (§3.4). Attention-DP ranks run as parallel schedulers in lockstep, so a step costs as much as its slowest rank. Output. Per-request TTFT, ITL, TPOT and end-to-end latency give medians and tails, and their totals give throughput per GPU and the hit rate per replica. The tuning agent receives these numbers for each candidate. They come from the same step cost model the analytical predictor uses, so the two agree when queueing and cache effects are absent, and the DES adds those effects when they are present. A.2 Speculative decoding model An anchor measured with speculation already contains the draft cost and the acceptance. Elsewhere ROCm InferaSim models the drafter. MTP and EAGLE-3 heads are built from the target’s own layer types, so each drafter layer is priced as a target layer of the same kind, plus the language-model (LM) head and sampling, at the drafter’s vocabulary and context. The number of drafter layers is a parameter: MTP defaults to the model’s MTP layer count and EAGLE-3 to one dense layer over a pruned vocabulary, and a model card or flag can change either. DSpark [10] defaults to a three-layer MoE backbone per block plus a light serial head, and n-gram drafting is free. In anchored mode the draft cost is the measured step scaled by the modeled ratio of draft time to step time. A verify step at depth k commits L(k) = 1 + aj (2) tokens, where aj is the probability that draft token j is accepted given that tokens 1..j−1 were. For models where InferenceX [46] publishes measured acceptance lengths, ROCm InferaSim takes L(k) from them. Other models use the sibling head’s curve (MTP for EAGLE-3 and vice versa) or the drafter’s default, the per-depth median over InferenceX models. Beyond the last measured depth, L is extrapolated with a geometric acceptance chain fitted to the measured points. Acceptance also depends on how predictable the text is. SPEED-Bench [1] measures it in six domains, which ROCm InferaSim groups into three optional entropy classes: low (coding, math), mixed (science, question answering) and high (writing, roleplay). The measured curves count as coding, and a class scales the first-position acceptance by its mean rate relative to coding. When the depth is left open, ROCm InferaSim tries every depth from 0, meaning no speculation, up to the limit and keeps the one with the most tokens per unit of step time at the projected batch, so it speculates only when that pays. On 43 measured MTP runs, anchored mode with the drafter model is nearly as accurate as on runs without speculation (§5.9). B.2 Communication Per layer, the kernel charges two TP all-reduces (one under attention DP). Per MoE layer, it charges an EP dispatch and combine. Per step, it charges p point-to-point hops across pipeline stages (§B.4). Every collective costs a latency plus a bandwidth term, t = α + m/B, on one of two tiers. Inside a node. Decode messages are small. Below 8 MiB, vLLM does not call RCCL [5]; it uses its own one- and two-shot custom all-reduce. Inside a step we charge only m/B, because α is the per-kernel launch and occupancy cost that the step already charges for every kernel it issues. Traffic that leaves the node crosses the network interface cards (NICs). We price it from the NIC datasheet bandwidth and a per-message latency, and hierarchical collectives combine the two tiers. Pipeline stages are placed contiguously, so a pipeline over n nodes has n−1 forward boundaries on the network, plus the token return from the last stage to the first. All other hops stay on xGMI. §G validates both tiers on one and two nodes. For those we use the size the engine reports, so admission is always simulated against the real pool. B.6 KV cache below HBM The DES models the tier as a second level of its block cache. Blocks evicted from HBM by the engine’s leaf-first LRU rule move to DRAM and are dropped only when DRAM is also full. A request whose prefix is DRAM-resident has those blocks promoted back, and the DES queues the transfer on the host link of its rank before scheduling the request, so a load adds to that request’s TTFT and does not stall other requests’ steps; loads that arrive together queue behind each other. The tier’s size is the DRAM each run hands its engine, divided over its GPUs (256–2,399 GB per node here), and the link is rated at the host-to-device bandwidth. Hits are therefore an output of the replay: a tier that is too small for the sessions in flight recomputes them, as the engine does. The four offload engines share this model and differ in their DRAM budget and in the scheduler they sit under. Covered offloaded runs are predicted within 4–16% on throughput per engine, and within 6% where the tier is added to an anchor measured without one (§5.6). In the Pareto sweep the tier is an input, its size per GPU and its link bandwidth, and the frontier is drawn with KV in HBM only and with a DRAM tier.

## E
Harvest checks

An anchor is only as good as the conditions of its harvest, so ROCm InferaSim keeps those conditions in the artifact. Each check below stops a measurement from silently describing something other than the deployment. We validated each check on measured runs. None is a fitted correction. The remedy is always to record and check, then re-harvest or refuse. The prompt length is recorded. The attention backend decides whether an anchor transfers across prompt lengths. We applied the same 8192-token DeepSeek-V4 anchor at 1024 tokens. On SGLang, whose backend reads a fixed top-k of the cache, it is within 3%. On vLLM’s dense MLA path, it is 41% high (18.96 vs. 13.44 ms). So anchors keep their decode sweep’s prompt length, and sweeps at two lengths give a per-token decode slope. Weights are real. An untrained router spreads tokens evenly over experts. With random weights, GLM-5.2 decode is 1.337× too fast at batch 64 and 1.045× at batch 4, and the gap grows with batch, as expert imbalance would cause. Anchors record whether weights were real, and the harvester uses real checkpoints. Prefix caching is off during harvest. A length sweep reuses its own prefix by design. With caching on, a DeepSeek- V4-Pro sweep gave 68–89 ms across 1024–8192 tokens at R2 = 0.995; with caching off, it gave 143–782 ms. ## I
Anchor artifact

An anchor is one JSON file per (model, engine, anchor-defining choices, width). Its fields: • Signature: accelerator architecture, engine and image, model checkpoint, weight/activation/KV/expert dtypes, attention and MoE backend, graph-capture mode and sizes, speculative method, TP/EP/attention-DP width. • Decode sweep: median ITL of a single wave at each captured batch size, at a recorded prompt length. Optional sweeps at a second prompt length enable context differencing. • Prefill sweep: TTFT at concurrency 1 for five prompt lengths with prefix caching off, and the fitted F, c1, c2. • Packed-prefill probe (optional): step time with k sequences of the billed length. The token budget is recorded so serialization can be detected. • Provenance: harvest timestamp, node, whether weights were real, whether prefix caching was off, and the client command line. Anchors live in a cache directory, and projection selects them by signature; a benchmark is rerun only for a kernel set or width the cache does not hold. Projection refuses an anchor whose accelerator or engine differs from the target. If its prompt length, width or packing length differs, projection uses it but flags it.

## J
Tuning agent details

Input: model card, cluster, objective, SLO budgets, request profile, lever list. Ledger: every trial with its configuration, metrics, legality and reason. 1. Seed. Build the baseline. Emit the ordered seed list (TP, attention DP, precision, load, scheduler, speculation, EP and MoE options, collectives, disaggregation). Keep the first Nseed legal, distinct seeds. 2. Score. For each candidate: check structure; project it with the anchor of its parallel shape; reject it if memory exceeds the HBM cap or a latency budget is missed; log it. 3. Plan. The planner LLM reads the ledger and emits hypotheses and 5–8 partial configurations as JSON. 4. Investigate. A recursive LM runs the plan with tools: evaluate, read history, read best, read budget, write notes, ask a sub-question. Each evaluation goes through step 2. 5. Stop when the budget is used, or when the best trial has not changed after 70% of the budget. Return the best legal trial. Mix planner: for each model and tier, project every candidate, keep those that meet the tier with margin, and select one (§4.1). Figure 11: The ROCm InferaSim tuning agent. Each candidate costs one projection of under half a second, and no GPU. Fusions. Fusions enter the search like any other lever, and every trial reports which fusions would pay off. The legality check has three rules. It offers the quant-fed patterns only with low-precision activations and the MoE patterns only on MoE models, and it rejects a list that repeats a fusion or combines named fusions with the generic flag. The seed planner adds the full legal set and its BF16-safe subset. Every trial reports its fusion opportunities, the legal fusions worth at least 2% of that trial’s decode step, largest first. What the LLM sees. Both stages receive the same five inputs as JSON or compact text: the architecture record (layers, hidden size, heads, MoE and sparse-attention fields), the target cluster (nodes, GPUs per node, HBM), the legal value set of every lever, the objective and its direction, and a summary of the trials so far (the 40 most recent, §4). The operator may add free-form guidance, and a scratchpad carries notes across rounds. Planner prompt. The planner is asked to design a search before using any tool: which levers are most likely to move the objective for this model, cluster and request profile, in what order to try them, and what to do if they fail. The prompt names the trade-offs to account for: latency against throughput (batch, concurrency, request rate), KV capacity (KV dtype, memory fraction, block size), prefill cost (chunk size, token budget), MoE communication (EP, DeepEP, load balancing), disaggregation, and the kernel options. It returns a short rationale, at most five testable hypotheses, 5–8 partial configurations as a JSON array ordered from most to least promising, and a polish plan. A partial configuration names only the levers it changes; the rest come from the baseline. Investigation prompt and tools. The search stage receives the plan and runs a loop. In each iteration it reads the scratchpad and the history, picks a configuration not yet tried, evaluates it, and every 3–5 evaluations writes what it learned. It stops when the budget is spent or the incumbent stops improving. Its tools are: evaluate a configuration (one projection, returning metrics, a signed score and, if the configuration is illegal, the reason); read the history; read the incumbent; read the legal sets, architecture, cluster and objective; read the remaining budget; write or read the scratchpad; and ask a sub-question of the same LLM. It returns the best configuration, a summary of what worked, and suggested follow-ups. Guards. The LLM never prices a configuration. Every proposal goes through the same structural check, memory cap, SLO check and projection as the seed sweep’s, and a value outside a lever’s legal set is rejected with its reason. Sparse attention is offered only at the width the checkpoint was trained with, and, when the operator lists validated weight precisions, only those are offered. The 192 searches scored 56,328 candidates, about 293 per search, including the seeds.
