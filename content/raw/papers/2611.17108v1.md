## 摘要

Memory decides which LLMs an edge device runs, and how fast: capacity on a $4$ GB Jetson Nano, bandwidth on an $8$ GB Jetson Orin Nano Super. Deployed formats (GPTQ, AWQ, $\texttt{llama.cpp}$'s K- and I-quants) spend equal bits on every integer code of a matrix, although the codes are far from uniform. $\texttt{LazyWeights}$ keeps these formats but tunes GPTQ so the codes compress, Huffman-codes them losslessly in interleaved lanes, and decodes them on demand in a small unit between DRAM and L2, so GPU kernels run unchanged and DRAM moves only coded bytes. At $1\%$ and $3.5\%$ perplexity budgets, coded Phi-3-mini, Mistral-7B and SmolLM-1.7B are $5.7-31.4\%$ smaller than the best $\texttt{llama.cpp}$ format. A bit-exact $0.21$ mm$^2$ ASIC decoder unit ($1$ GHz, $7$ nm) cuts Orin latency and energy per token by up to $36\%$ and $38\%$ ($54\%$ and $44\%$ with prompt-lookup speculation). On the Nano, $\texttt{LazyWeights}$ needs $58-64\%$ less time and $53-57\%$ less energy per token than CPU $\texttt{llama.cpp}$, and runs a streamed Mistral-7B 6.6$\times$ faster at $3.89$ bits per weight. A Huffman decoder beats an rANS decoder in rate and area at equal throughput; the ASIC decoder unit runs bit-exact on a Zynq UltraScale+ FPGA (AMD ZCU102).

Introduction Generating a token reads every weight of a large language model (LLM) once, so on an edge device the weight footprint decides whether a model fits and how fast it runs: a 7B model needs 14 GB in 16-bit floats, more than most edge modules have, and even at 4 bits each token moves gigabytes through a phone-class memory system. llama.cpp [1] has made post- training quantization the default, with GGUF files offering fixed-width integer formats with per-block scales from 8 down to about 3 bits per weight. removes software decoding and the coded size decides whether Mistral-7B runs at all (Table I). Our contributions: • Entropy-aware quantization in standard formats: GPTQ with shared sub-block steps and a wider step, emit- ting valid GGUF 5.7–31.4% smaller than the best llama.cpp format at ≤1% and ≤3.5% ∆PPL. • A parallel-decodable Huffman bundle: a length-limited canonical code per matrix, 32 interleaved lane streams per tile, pair symbols for 4-bit codes; within 1.2–2.1% of the zeroth-order entropy, all overheads included. • A Huffman decode unit between DRAM and L2: 0.05 mm2 per 32-lane engine at 1 GHz (ASAP7), sized from the bandwidth, bit-exact, prototyped on an AMD ZCU102; never larger than rANS in rate, smaller in area at equal throughput. • End-to-end evaluation in two edge regimes: latency and energy per token on a Jetson Orin Nano Super and a Jetson Nano, greedy and with prompt-lookup speculation, against llama.cpp, from measured time, energy and DRAM energy per byte and synthesized decoder power. These formats and the quantizers that target them (GPTQ [2], AWQ [3], the llama.cpp K- and I-quants) share an unstated commitment: every code of a matrix costs the same number of bits. This wastes bits twice. Weights are bell-shaped, so a 4-bit alphabet’s inner codes dominate and its entropy sits well below 4 bits [4], [5]; and many code assignments reach the same quality, so a quantizer that knows its codes will be entropy-coded can pick ones that compress. Lossless weight coding, from Deep Compression [6] to recent work on 16-bit LLM weights [7]–[10] or a quantizer’s integers [11], [12], takes the quantizer as given and mostly decodes in software. A coded 4-bit model is worth having only if it beats the next-smaller fixed-width format at equal quality, a comparison rarely made, and only if its codes can be expanded at DRAM rate every token: software decoders fall 15–20× short of that on an Orin Nano Super, making a token 2.5–3.2× slower than the same codes at fixed width. II. Related Work Weight quantization. GPTQ [2] quantizes column by col- umn, feeding each column’s Hessian-weighted error into the rest; AWQ [3] rescales salient channels. Both target fixed- width formats, like llama.cpp’s [1] K- and I-quants (op- tionally with an importance matrix), which edge models ship in and which are our baseline. AQLM [13], QuIP# [14] and QTIP [15] reach lower rates at equal quality with vector and trellis codebooks but need their own formats and kernels; we keep the deployed scalar format and code its integers. LazyWeights removes the commitment end to end (Fig. 1). It shapes the codes inside the deployed format, codes them with a Huffman layout built for parallel decoding, and decodes them in a small unit between DRAM and L2, where bytes are counted. The GPU still reads fixed-width codes, so its kernels are untouched, the decoded weights are bit-identical to a valid GGUF file, and quality is the quantizer’s alone. H(q) ≈h(w) −log2 ∆, h(w) = − p(w) log2 p(w) dw, (2) so scaling the step by c saves about log2 c bits per weight: 0.32 at ×1.25, 0.58 at ×1.5. At 4 bits, far from that regime, the measured saving is smaller (0.19–0.20 b/w at ×1.25 on Phi-3, 0.46 at ×1.5 on Mistral), but the lever is the same. Conversely, a quantizer that spreads codes evenly, as min-max fitting per sub-block does, pushes H(q) toward the full width: the coder’s saving is decided by the quantizer. Where we sit. LazyWeights is, to our knowledge, the first design to code the deployed integer format rather than merely store it: it shapes the codes inside llama.cpp’s formats, keeps files valid GGUF, decodes in hardware where DRAM traffic is counted, and compares against the best fixed- width format at equal perplexity, the comparison that decides whether coding is worth its decoder. Any quantizer that emits integer codes in a fixed format can feed the bundle and the unit.

A lossless Huffman bundle built for parallel decoding Huffman decoding is sequential: a code’s start is known only once the previous code is decoded. The bundle (Fig. 3a) breaks this. Each matrix has one canonical code, length-limited to 11 bits so an 11-bit window always resolves a code. Each 64×256 tile is 32 lane streams of two rows, decoded in parallel without waiting for each other. The lanes’ 32-bit words are interleaved, so the words needed next are adjacent and a GPU warp or the unit’s read port fetches them in wide, aligned reads; per-tile lane offsets let any tile start independently. In 4-bit formats two codes form one 8-bit pair symbol, two weights per decode step. FPGA prototype. We map four engines onto an AMD ZCU102: a Zynq UltraScale+ XCZU9EG MPSoC (speed grade −2; 274k LUTs, 548k flip-flops, 32.1 Mb of block RAM, 2,520 DSP slices) with a quad-core 1.2 GHz Arm Cortex-A53 running Linux, 4 GB of 64-bit DDR4 on the processor side and 512 MB of 16-bit DDR4 on the fabric side. The Arm cores write each matrix’s bundle in chunks into block RAM over AXI and start the engines together; every lane’s output (CRC-32) and every chunk’s cycle, stall and word counts are checked against the C model. E. Runtime D. A Huffman decode unit between DRAM and L2 Our runtime runs both the twin – the same codes without entropy coding, as the GPU sees them behind the unit – and the coded bundle, decoded inside the GEMV kernels as the software reference. A fixed-order reduction across tile columns, in the int8 and fp32 kernels, makes the two bit- identical, so losslessness is tested end to end: identical logits on both devices, and speculation (up to 8 tokens per pass) token-identical to greedy. Decoding in the GPU kernels spends instructions on bit manipulation, costing more time than the bytes save; expand- ing weights back into DRAM saves storage, not bandwidth. LazyWeights decodes between the memory controller and L2 (Fig. 3b): DRAM holds and moves only coded weights, L2 receives fixed-width codes, and the kernel is unchanged, so the first term of (1) follows the coded size. Lane. A request side feeds the lane’s stream through a 4- entry prefetch FIFO into a 64-bit bit buffer. The next 11 bits are compared against 11 per-length limits at once; the thermometer result gives the length, the symbol is the code plus a per-length offset, and the buffer shifts. A lane emits one pair symbol (two weights) per cycle; the per-matrix limit and offset tables are broadcast by the engine. Speculation. Attention reads each key and value once for all draft tokens of a head, with per-query arithmetic independent of the draft length, and Q5 K/Q6 K twins keep the GGUF width (nibbles plus a high-bit plane), not bytes (Table II). Nano kernels. The instruction-bound Nano needs few in- structions per weight. A 32-bit fetch yields four (5/6-bit) or eight (4-bit) fixed-width codes; Q5 K/Q6 K codes are rebuilt from their nibble and high-bit planes by byte permutes, one sub-block per fetch. Byte permutes also replace integer-to-float conversion (a code placed under the exponent of 223, recovered by one subtraction) and table lookup (the 16 IQ4 XS grid values, biased to unsigned bytes); the multiply-add order is unchanged. The ordered reduction replaces Maxwell’s slow global atomics. Limitations and Conclusion The unit’s latency and energy are projections from measured device numbers and pre-layout synthesis, not a fabricated SoC; the FPGA shows bit- and cycle-exact decoding, but at FPGA clocks, not 1 GHz. For streamed Mistral-7B the twin is no proxy for the unit: it streams the fixed-width bytes (1.05 GB per token at a 2560 MB budget vs 0.68/0.26 GB coded at ≤1%/≤3.5%), leaves less than our memory floor free, and at a 2048 MB budget from the SD card was 1.2–1.8× slower than software decoding. We therefore do not report the unit’s streaming time; reading its coded bytes alone takes 2.2/0.8 s per token from USB. We did not evaluate Llama-3 or Qwen3, which quantize worse [23], or long contexts, where the uncoded fp16 KV cache dilutes the saving (Mistral-7B at 4K tokens: 0.54 GB per pass vs 3.5 GB of weights). The fixed width of edge LLM formats is a commitment, not a necessity: the codes are far from uniform, the quan- tizer can make them less so at no quality cost, and an entropy coder removes the difference if the decoder sits where bytes are counted. Shaped and Huffman-coded, models in llama.cpp’s formats are 5.7–31.4% smaller at equal perplexity; a 0.2 mm2 unit between DRAM and L2 turns this into faster, cheaper tokens on a bandwidth-bound Orin Nano Super, with or without speculation, and lets a capacity-bound Nano run a 7B model that otherwise does not fit. Coding the KV cache, newer model families, and a layout next to a real memory controller are independent next steps.
