## 摘要

On-demand model loading dominates response latency for interactive on-device AI, yet unified memory architectures (UMAs), now common on edge devices, should make it cheap by placing weights in memory the GPU already sees. However, frameworks still use the loading flow built for discrete GPUs, leaving significant inefficiencies. This paper presents UMLoad, a system-level model-loading accelerator that decouples a framework's logical allocations from their physical page backing. UMLoad uses on-demand reconstruction to eliminate the weight copy while preserving copy independence, and GPU-assisted page zeroing to accelerate runtime allocation while preserving its security guarantee. UMA suits these workloads: it lets memory-limited devices hold larger mod- els and longer contexts, and in principle removes CPU–GPU transfer from loading, as the GPU already sees weights in memory. Model loading can dominate cold-start response latency on mobile devices [75], and measurements across commercial smartphones show substantial model-preparation delays [74]. Loading costs are especially exposed when in- ference consists of a short subtask; long-context prefill and lengthy generation can narrow the gap. On UMA, this creates two inefficiencies (Figure 2). First, weight transfer is redundant: it preserves buffer independence and loader portability, but duplicates weights already in shared mem- ory, adding copy latency and doubling their peak memory (3.7 GB extra for Qwen3-1.7B). Second, runtime allocation forces synchronous page zeroing: GPU allocations draw from system memory, which the OS must zero to prevent cross-process leaks. Zeroing the 6 GB KV cache takes 0.63 s, as the CPU achieves under a third of the 89.6 GB/s memory bandwidth. and cache maintenance remain substantial. UMLoad com- bines two techniques to turn fast GPU zeroing into fast alloca- tion. First, it splits each allocation request into page batches and pipelines CPU work with GPU zeroing across batches, overlapping CPU and GPU execution. However, CPU work can still outlast GPU execution and leave the GPU waiting between batches. Second, it shortens CPU stages by preparing GPU mapping resources ahead of time to reduce per-batch mapping work and parallelizing cache maintenance. Together, these techniques allow allocation throughput to approach the GPU’s zeroing throughput. Throughout, pages are still zeroed before use, preserving the security guarantee (§5). Existing solutions do not close this gap. NVIDIA GDS [46] streams weight files from SSD directly into GPU memory on supported configurations. Zero-copy interfaces [44] offer the right abstraction, but deliver incon- sistent performance across frameworks and platforms and require intrusive, per-framework changes to the loader. Be- sides weight transfer, synchronous page zeroing remains a runtime-allocation bottleneck on the tested platforms (§2.2). UMA thus calls for a loading mechanism that (G1) eliminates weight transfer rather than overlapping it, thereby also avoid- ing the staging memory that pipelined loaders need; (G2) accelerates synchronous page zeroing on the allocation path while preserving its security semantics; and (G3) generalizes across UMA platforms and integrates with existing inference frameworks with little or no modification. Reusing source pages must preserve independent CPU and GPU buffers. Di- rect sharing allows later CPU writes to affect GPU contents. Unconditional ownership transfer is also insufficient: CPU contents must remain accessible, but sources without file backing cannot be reconstructed after handoff. UMLoad uses on-demand reconstruction: it transfers exclusive ownership of file-backed pages in an aligned, huge-page layout to the GPU and reconstructs the CPU source in separate pages only upon later CPU access. This preserves copy independence while supporting ordinary GPU reads and writes. The aligned, con- tiguous huge-page mapping preserves efficient GPU address translation. During model loading, the CPU rarely accesses these pages afterward, so reconstruction is almost never trig- gered, preserving copy independence with virtually no addi- tional memory overhead (§4).

Quantization reduces the weight representation size [13, 28, 32, 75], while contextual spar- sity enables selective weight loading [4]. Pruning reduces the number of nonzero weights [12]; reducing file I/O addi- tionally requires a representation and loading path that omit those zeros. Other approaches retain resources in pools and caches [45, 81] or optimize prefetching and eviction during loading [34]. These techniques reduce transferred data or ex- ploit reuse and overlap. They can complement UMLoad’s elimination of redundant weight copies and acceleration of fresh-page zeroing. The two loaders expose different costs. llama.cpp allo- cates weight memory and prepares upload buffers before the pipeline starts, leaving 0.13 s on AMD and 0.41 s on NVIDIA not overlapped. It also issues H2D copies on the same thread as file I/O, leaving API submission work on the critical path and adding 0.085 s on AMD. PyTorch uses multithreading to overlap both weight allocation and H2D copies with file I/O, but staging-buffer preparation and remaining exposed work still cost 0.15 s on AMD and 0.47 s on NVIDIA. Bypassing weight transfer. Drivers offer APIs that help to achieve zero-copy or even skip weight trans- fers between GPU and CPU on UMA platforms. Host- registration APIs expose existing host buffers to the GPU (e.g., cudaHostRegister), while shared-allocation APIs provide memory accessible to both processors (e.g., cudaMallocManaged) [44]. Finally, NVIDIA GPUDirect Storage (GDS) reads files directly into GPU buffers on sup- ported configurations, bypassing host staging [46]. However, adopting these mechanisms requires changes to framework loading paths. In addition, shared allocation still incurs slow zeroing on all tested UMA platforms. For writable private source mappings, host registration can incur synchronous copy-on-write during registration (§7.2). Finally, on DGX Spark, GDS supports only compatibility mode, preventing use of its native storage-to-GPU DMA path [47]. Using a pipeline to reach this bound is not free, either. The staging buffer that lets Run:ai reach high pipeline effi- ciency scales with the model, growing from 3.7 GB at 1.7B to 10.4 GB at 7B. The llama.cpp asynchronous loader requires fewer staging buffers, but the minimum buffer size is still de- termined by the model’s largest tensor (about 10% of the total weight size). Finally, neither evaluated pipeline accelerates synchronous zeroing of fresh runtime pages.

## 4
On-demand Reconstruction

4.1 Eliminating Weight Allocation and H2D Copy Weight transfer comprises two operations: allocating GPU buffers for weights and populating them with host-to-device (H2D) copies. On UMA, the source pages already reside in shared physical memory. The straightforward approach is therefore to let the GPU directly access the pages backing the H2D copy source, eliminating redundant physical-page allocation and the H2D copy. Architecture. Figure 6 provides an overview of UMLoad. It spans the user-mode driver (UMD) and the kernel-mode driver (KMD), and requires no changes to framework code on supported paths. The Page Reclaimer (§4) implements On- demand Reconstruction. Its ReclaimPage API identifies eligible page-cache pages through H2D source ranges and reclaims them with exclusive ownership as the destination buffer’s physical memory. These reclaimed pages replace weight transfer. Later CPU accesses reconstruct the source contents from the backing file in separate physical pages. The Page Zeroer (§5) accelerates runtime memory allocation by offloading page zeroing to the GPU. It accelerates the allocation of private pages, zeroed system pages managed by the driver, for buffer ranges not covered by page reclamation. First, UMLoad replaces intercepted allocation calls with CreatePBO, which reserves GPU addresses while postpon- ing physical-page allocation. On the loading paths represented by Algorithm 1, H2D copies initialize weight buffers before GPU computation uses them. The PBO’s physical backing can therefore remain open until H2D calls supply the source addresses and byte ranges. Second, when an H2D call targets an open PBO, UMLoad invokes ReclaimPage to obtain the physical pages backing the source range, faulting them in if necessary, and installs them as the corresponding des- tination range’s backing. Before the PBO’s first consuming operation other than an H2D copy, UMLoad finalizes it and establishes GPU page-table entries mapping these pages at the framework-selected destination addresses, allowing the GPU to directly access their contents. The completed PBO then supports ordinary GPU operations. UMLoad uses a provisional buffer object (PBO) to decou- ple a framework-visible GPU allocation from its physical backing. A PBO exposes the handle, size, and GPU virtual address (GVA) of an ordinary GPU buffer object (BO), but leaves its backing open for construction from either reclaimed pages or private pages. Internally, a PBO maintains an array of page slots and an ownership bitmap that distinguishes the two: an empty slot is UNBOUND, and a populated one is RE- CLAIMED or PRIVATE. Both classes reside in UMA system memory and differ only in origin and release path. One PBO can therefore combine several reclaimed and private ranges under a single framework-visible GVA and lifetime. Before forwarding a PBO for GPU execution, UMLoad completes its physical backing by filling the remaining UNBOUND slots with PRIVATE pages supplied by the Page Zeroer. The PBO then behaves as an ordinary GPU buffer object in any subse- quent GPU operation. Direct page mapping requires the source and destination to have the same in-page offset, whereas H2D copy arguments may have arbitrary byte offsets. To match these offsets, during a one-time preparation run, UMLoad records each weight tensor’s framework-selected GPU VA. It then rewrites the weight file using PADDING: given the current absolute file offset c and a recorded destination d, it inserts (d−c) mod P padding bytes, where P is the base-page size. ## 5
GPU-Assisted Page Zeroing

UMLoad’s Page Zeroer offloads page zeroing to the GPU to accelerate runtime memory allocation on UMA. It pipelines CPU submission, GPU execution, and CPU cleanup, then reduces CPU work to keep the pipeline supplied with zeroing tasks. Pipelining zeroing tasks. To overlap this CPU work with GPU execution, UMLoad splits each request into smaller page batches, each processed as one zeroing task. UMLoad chooses the per-task size to be the smallest that does not incur a visible GPU bandwidth drop (1%), because extra per-task submission costs can be overlapped with GPU execution, and smaller batches mitigate bubbles at the start and end of the pipeline. The three stages then overlap across batches (Fig- ure 7): the CPU prepares and submits task i + 1 while the GPU executes task i, and a separate cleanup worker processes earlier completed tasks. Task order is preserved, and comple- tion fences are used to track per-task status. At Finalize, UMLoad checks the completion fences and waits until the pages are ready. For the same 4 GiB request, pipelining re- duces latency from 59.76 to 29.64 ms. However, CPU sub- mission takes 28.8 ms, exceeding the 25.6 ms GPU execution time. Preparing the next task can therefore limit the pipeline’s throughput. GPU zeroing. CPU zeroing accounts for much of runtime memory allocation (§2.2). A straightforward approach is to offload it to the GPU. The KMD creates an execution context and keeps the zeroing program available across requests. It processes each request through three sequential stages before starting the next: 1. Task submission. The CPU acquires raw physical pages, performs required cache maintenance to make them ac- cessible to the device, installs GPU VA mappings, and prepares task descriptors, command buffers, and comple- tion fences before submitting the task. 2. Task execution. The GPU writes zeros to the mapped pages. Following open-source driver implementations, the KMD builds command buffers that issue hardware fill commands or launch a precompiled zeroing kernel (detailed in §6). 3. Task cleanup. After GPU completion, the CPU performs required visibility operations, releases GPU mappings and task resources, and returns pages to the driver’s allocation path. Reducing CPU overhead. First, the Page Zeroer creates a pri- vate GPU address space, reserves GPU virtual addresses, and installs the page-table hierarchy during initialization. Each task updates existing page-table entries for newly acquired pages and patches arguments in the command templates. This avoids repeated page-table and VA allocation and reduces mapping and task cleanup. Second, cache maintenance re- quires sequentially issuing flush operations across the entire memory range. UMLoad uses multiple CPU workers to ac- CPU work after GPU offloading. The CPU performs task submission and cleanup. Offloading zero stores leaves page and resource management on the CPU. ## 6
Implementation

We implement UMLoad using open-source drivers on Intel and AMD UMA platforms, and extend the implementation to NVIDIA with a closed-source UMD. Table 1 lists the modified components and their lines of code (LoC) on each platform. UMD interposer. On AMD and Intel, the interposer is in- tegrated into the userspace driver; the modified APIs are limited to memory management and submission paths that resolve buffer-object metadata. On NVIDIA it is a load- able library that interposes the same API classes and uses cuMemAddressReserve to reserve a private range of GPU virtual addresses for UMLoad to manage exclusively. UMLoad provides two primitive APIs on NVIDIA GPUs for frameworks to mark their model-loading phases, during which UMLoad interposes on memory operations. This explicit tag- ging is necessary to restrict UMLoad’s independently man- aged memory range to weight tensors. Interposing runtime memory allocations can lead to failures when the CUDA run- time calls APIs that UMLoad has not implemented through manual implementations.
