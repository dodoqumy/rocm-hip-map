## 摘要

As GPU accelerators grow larger to meet rising compute demands, they exhibit increasingly pronounced non-uniform memory access (NUMA) characteristics that challenge existing LLM frameworks. Chiplet-based architectures provide a practical path to larger GPUs while mitigating manufacturing yield constraints. Modern GPUs such as AMD Instinct MI300X employs such a multi-die design, and further offer GPU partitioning capabilities, partitioning a single physical GPU into multiple logical devices with NUMA-aware memory domains, promising faster kernel launches, and reduced memory access latencies with improved locality. However, current parallelization strategies, designed for homogeneous GPU topologies, when applied under partitioning, extend its unidimensional sharding causing significant performance degradation. Three bottlenecks emerge: (1) memory redundancy; (2) arithmetic intensity collapse; (3) communication overhead from flat collectives. We present Starscream, a rethinking of LLM sharding for the chiplet era. Rather than stretching inter-GPU sharding thinner, Starscream adds intra-GPU sharding along an orthogonal dimension, grounded in three foundational principles: kernel shape preservation, memory redundancy elimination, and communication overhead minimization. These principles form the basis for extending any sharding strategy into the partitioning regime. We demonstrate their effectiveness using tensor parallelism as a case study. On AMD MI300X and MI355X, exploiting partitioning capabilities yields up to 4x speedup for attention and 1.43x for fused GEMMs compared to chiplet-oblivious baselines, demonstrating the effectiveness of chiplet-aware designs. Starscream's principles generalize across sharding strategies and future architectures.

Larger dies suf- fer from exponentially decreasing yields as the probability of a defect appearing on any given die increases with area. Chiplet- based architectures have emerged as the industry’s response to this challenge [37]. By decomposing a large monolithic design into multiple smaller dies interconnected through advanced packaging technologies, vendors can maintain high yields while still delivering aggregate compute density that would be hard with a single die. ## I. INTRODUCTION

The computational demands of large language models (LLMs) have driven an unprecedented expansion in GPU capabilities. Modern accelerators such as AMD’s Instinct MI300X offers a peak FP8 throughput of over 5 petaflops and 192 GB of HBM3 memory, while the following generation MI350 Series GPUs offers even greater performance through architectural refinements and superior memory bandwidth and capacity [7]. This trajectory shows no signs of slowing: as foundation models grow from hundreds of billions to trillions of parameters, hardware vendors continue to scale accelerator designs to meet demand [44]. Alongside compute scaling, memory bandwidth has evolved in lockstep. HBM has progressed with each generation, de- livering substantial improvements in both capacity and band- width [8]. The MI300X, for instance, provides up to 5.3 TB/s of aggregate HBM bandwidth, a figure that will only increase with subsequent generations (e.g., up to 8 TB/s in MI350 Series GPUs). Yet these impressive bandwidth figures mask a critical architectural reality: this bandwidth is not uniformly accessible from all compute units. We present Starscream, a rethinking of LLM execution for partitioned GPUs. The core insight: leverage the coarse- grained control over data placement and compute mapping that partitioning modes provide to maximize data locality and minimize cross-die accesses. Rather than treating partitioned GPUs as simply “more GPUs,” Starscream recognizes that partitioning exposes a new level of hierarchy, and composes existing parallelism strategies hierarchically—applying each at the level of the topology where it is effective to extract performance from the same compute resources. This principle yields a systematic set of techniques: AMD Instinct GPUs provide explicit mechanisms to exploit this inherent NUMA topology. Compute Partitioning modes logically divide the compute units (CUs) within a single physical GPU into independent virtual GPUs: DPX for 2-way, QPX for 4-way, and CPX for per-XCD granularity (8-way on MI300X). Each virtual GPU is capable of running separate workloads with dedicated compute resources. Complementing compute partitioning, the Memory Partitioning (NPS) mode subdivides the HBM address space into NUMA domains. In NPS4 mode on MI300X, each NUMA domain encompasses the memory attached to a single IOD, enabling workloads to achieve higher effective bandwidth by localizing memory accesses to nearby controllers [6]. We will refer to these capabilities collectively as partitioning. Figure 1A illustrates this chiplet-based architecture. At peak isolation, these partitioning modes unlock signifi- cant architectural benefits. Operating MI300X in CPX+NPS4 mode (8 virtual GPUs mapped across 4 NUMA domains) with no cross-die communication, provides substantial advantages over the default SPX+NPS1 configuration [10], [11]: • Eliminating memory pressure: Hierarchical sharding avoids replicating data structures that naive sharding duplicates—KV caches in TP inference, parameters in FSDP training—preserving memory capacity and bandwidth. • High Arithmetic Intensity GEMMs: 2D sharding main- tains arithmetic intensity even as parallelism increases, keep- ing operations compute-bound rather than memory-bound. • lower kernel launch latency: Avoiding L2 cache flushes between kernel runs, formerly required to preserve coher- ence across XCDs. • Hierarchical collectives: Collectives structured as two- level operations: fast intra-GPU operations over USR links, followed by inter-GPU synchronization on XGMI. • over 20% faster computations: HBM accesses limited to the local die reduce signal travel distance and eliminate contention on shared resources [10], [11]. • Computation-communication fusion: Overlaps kernel exe- cution (attention, GEMMs, RMSNorm) with inter-XCD data movement, hiding collective latency behind computation. • Reduced IOD power consumption: Lower cross-die traffic decreases power dissipation in the IODs. However, peak isolation is unrealistic for modern LLMs. Model parameters and KV caches exceed single-partition capacity, necessitating sharding across multiple devices, and how we shard determines what overheads get exposed. We implement and evaluate Starscream on AMD Instinct MI300X GPUs, demonstrating that chiplet-aware design trans- forms GPU partitioning into a significant advantage. Our NUMA-aware paged-attention kernels achieve up to 4× speedup in CPX/NPS4 mode over SPX/NPS1. Our fused GEMM kernels with inter-XCD peer-mapping deliver 1.43× faster execution. These per-kernel improvements compound to yield substantial end-to-end throughput gains across diverse model architectures and batch sizes. Beyond raw performance, Starscream’s hierarchical sharding principles generalize across sharding strategies, offering a blueprint for exploiting NUMA topologies in future chiplet-based accelerators. Current frameworks—both inference (vLLM [30], TensorRT-LLM [40]) and training (Pytorch [46], [56], Megatron-LM [51])—see virtual GPUs as independent devices, unaware of the partitioned topology. Total node resources remain unchanged, yet existing frameworks view virtual GPUs as additional devices. Naively extending the intra-node sharding strategies to the higher device count, though intuitive, exposes three fundamental bottlenecks: (1) reduced memory capacity from redundant memory replication, (2) degraded arithmetic intensity as matrices become increasingly narrow, and (3) communication overhead from flat collectives that ignore the bandwidth hierarchy between inter-die and inter-GPU links (inter-die links offer 10× inter-GPU bandwidth [6], [12]). Baseline Operation: SPX NPS1 AMD Instinct GPUs can partition a single physical GPU into multiple compute and memory domains. We focus on the most aggressive configuration: CPX NPS4. In the default Single Partition Accelerator (SPX) mode with unified memory (NPS1), the GPU presents the illusion of a single monolithic device. The L2 cache appears shared across all XCDs, and HBM is accessible from any compute unit. Compute Partitioning (CPX) mode partitions compute resources at XCD granularity. Each XCD becomes an inde- pendent virtual GPU, receiving 1/8th of total HBM capacity. The XCD’s local L2 slice now becomes its private L2 cache. Memory allocation. Assuming a uniform memory distribu- tion, pages would be allocated to HBM slices in round-robin fashion across all dies. The first page goes to HBM slice 0 on IOD 0, the second to HBM slice 1 on IOD 0, the third to HBM slice 0 on IOD 1, and so forth. Memory Partitioning (NPS4). NPS4 mode partitions mem- ory into four NUMA domains, one per IOD. Each IOD’s HBM slices constitute a separate NUMA domain. With CPX NPS4, each XCD’s 1/8th memory allocation is exclusive to its local NUMA domain—the HBM slices connected to its IOD. Since each IOD hosts two XCDs, half of the IOD’s HBM capacity is allocated to each XCD. Data access paths. When a CU requires data, the access latency depends on where the data resides. If the data is in a local HBM slice—one connected to the same IOD as the requesting XCD—it is a direct read. However, if the data resides in a remote HBM slice on a different IOD, the data must traverse the USR ring: it is first read from the remote HBM to its local IOD, then transferred across one or more USR hops to the requesting IOD, and finally delivered to the XCD. For the farthest memory (two hops away), this path is significantly longer than local access. Bandwidth implications. In NPS1, each XCD can theoret- ically tap the aggregate bandwidth of all HBM slices across all IODs. In NPS4 on MI300X, each XCD can only access bandwidth from the HBM slices on the same IOD. This repre- sents a trade-off: reduced aggregate bandwidth accessibility in exchange for guaranteed local bandwidth without contention. E. Benefits of CPX NPS4 Mode C. A single physical GPU becomes several smaller vir- tual GPUs—each with reduced memory capacity, diminished bandwidth, a fraction of the L2 cache, and fewer compute units. The Orthogonal Sharding Principle The key insight behind Starscream is multi-dimensional sharding. When workloads are sharded across physical GPUs in a node along a given dimension, switching to partition- ing should not always extend that same sharding deeper— this is precisely what causes naive sharding to fail. Instead, partitioning should retain the work per physical GPU exactly as the ideal sharding for that GPU topology suggests, while introducing sharding along an orthogonal dimension across the virtual GPUs within each physical GPU. • Tensor parallelism is the dominant strategy for large- model inference, where latency-sensitive decode phases make partitioning’s locality benefits most attractive. • The three bottlenecks—memory replication, GEMM in- tensity collapse, and collective overhead—manifest most acutely under tensor parallelism with Grouped Query Attention models [4]. A flat all-reduce spanning all 64 virtual GPUs in MI300X bottlenecks on the slowest link—XGMI—leaving the faster USR fabric underutilized. a) Orthogonal Sharding Strategy: Instead of replicating the KV cache, Starscream shards it across compute partitions along the sequence length dimension. Each virtual GPU holds a subset of tokens, allocated in round-robin fashion: the first token’s KV entry resides on XCD0, the second on XCD1, and so on. Figure 5 illustrates this sharding. Each XCD retains its assigned query head from inter-GPU tensor parallelism, but rather than duplicating the KV cache, XCDs share a single distributed copy. This eliminates memory redundancy entirely. a) Three-Phase Hierarchical All-Reduce: Starscream re- structures all-reduce as a three-phase operation that decouples intra-GPU and inter-GPU communication. We illustrate using the 4-GPU, 2-XCD-per-GPU system from Figure 3, where each colored tile represents an M × N partial result. b) Computation with Distributed KV Cache: Since self- attention requires each query to attend over all KV tokens, the distributed cache necessitates coordination. Two approaches are possible: 1) Intra-GPU reduce-scatter (Phase 1): Each physical GPU performs a local reduce-scatter across its XCDs over USR links. As shown in Figure 6A, after this phase each XCD holds half the tile (shape M × N/2), containing the reduced result from both local XCDs. All physical GPUs execute this phase simultaneously with no cross- GPU dependency. 2) Inter-GPU peer-XCD all-reduce (Phase 2): XCDs at the same position across physical GPUs (all XCD0s, all XCD1s) perform an all-reduce over XGMI links. As shown in Figure 6B, after this phase each XCD holds the fully reduced result for its half of the tile—aggregated across all physical GPUs. 3) Intra-GPU all-gather (Phase 3): Each physical GPU performs a local all-gather across its XCDs over USR links. As shown in Figure 6C, this distributes the com- plete M×N result to all XCDs. Like Phase 1, all physical GPUs execute in parallel. b) Benefits: This decomposition provides two key ad- vantages. First, intra-GPU and inter-GPU communication are fully decoupled: the fast USR links handle Phases 1 and 3 without being throttled by slower XGMI traffic. Second, the inter-GPU all-reduce in Phase 2 operates over physical GPUs only (e.g., 8 participants), not virtual GPUs (64 participants), reducing XGMI traffic proportionally. Together, these ensure both network tiers operate at their respective peak bandwidths. 1) KV all-gather: Before computing each layer, all-gather the KV cache entries across XCDs. Each XCD then holds a complete copy, computes full self-attention locally, and evicts the gathered entries afterward—analogous to how FSDP all-gathers parameters per layer. 2) Query all-gather with partial attention: Keep KV en- tries in place and all-gather the query heads instead. Each XCD then holds all query heads but only its local KV subset, computing partial self-attention. These partials are then exchanged via a collective call, followed by a lightweight aggregation kernel. c) Decode versus Prefill: The choice between these approaches depends on the inference phase. During decode, the autoregressive nature produces exactly one query token per iteration, while the KV cache holds all tokens observed thus far. Notably, KV all-gather enables full local attention, eliminating the aggregation kernel. d) Effectiveness: This approach dramatically reduces inter-die data movement. ## VI. RELATED WORK

a) Chiplet GPU Coherence: Prior work addresses co- herence overhead in multi-chiplet GPUs assuming a shared coherence domain. HMG [47] extends coherence protocols hierarchically; CARVE [27] caches remote GPU data locally; CPElide [17] tracks inter-kernel dependencies to synchronize only when necessary, further improving performance. Starscream differs fundamentally: AMD’s CPX mode par- titions a GPU into independent virtual GPUs with pri- vate L2 caches and disjoint memory, eliminating coher- ence overhead entirely. This introduces new challenges— reduced per-partition capacity and explicit communication— that Starscream addresses via orthogonal sharding. Even with zero coherence overhead, partitioning’s NUMA locality bene- fits (faster local HBM, 3× lower kernel launch latency) remain inaccessible to unified-memory designs like SPX NPS1.

## VII. CONCLUSION

Non-uniform memory access is an inherent reality in mod- ern GPUs—whether from larger monolithic dies or chiplet- based designs. AMD’s compute and memory partitioning modes expose this topology, providing knobs to exploit the un- derlying NUMA hierarchy. With perfect isolation, partitioning delivers its full potential. But when a model exceeds a single partition’s capacity, efficient mapping is essential to maximize reuse and minimize communication; without it, redundant parameters, KV caches, skinny matrices, and flat collectives erode the architectural gains. In this work, we presented Starscream, which reframes partitioning not as “more GPUs” but as a new level of the compute and memory hierarchy, by composing existing parallelism strategies hierarchically and applying each at the level of the topology where it is effective. Concretely, Starscream eliminates redundant memory usage, sustains arithmetic intensity through 2D GEMM sharding, structures collectives around the intra-die/inter-die bandwidth gap, and fuses computation and communication to further improve performance. On AMD Instinct MI300X and MI355X GPUs, these techniques deliver up to 4× faster attention and 1.43× faster GEMM execution, transforming GPU partitioning into a net advantage—using the same compute resources, with no additional hardware. As chiplet counts continue to grow and NUMA effects deepen, Starscream’s hierarchical sharding principles offer a blueprint for extracting performance from the topology of future partitioned accelerators. b) Parallelism Strategies: Distributing LLMs across GPUs relies on established techniques: tensor parallelism (TP) shards weight matrices with all-reduce reconciliation [51]; se- quence parallelism (SP) shards activations along the sequence dimension for normalization and dropout [20], [28], [55]; context parallelism (CP) shards input sequences, exchanging KV tensors for full-context attention [1]; pipeline parallelism shards across layers [39]; expert parallelism routes tokens to sharded MoE experts [32]. Long-context LLMs have driven further refinements: Ring Attention [34] overlaps KV transfers with blockwise attention; Striped Attention [15] improves load balance via interleaved tokens; DeepSpeed-Ulysses [26] uses all-to-all for head-parallel attention; USP [21] and Loong- Train [22] unify these into hybrid schemes; DualPipe [19] overlaps forward and backward computation with communi- cation to minimize pipeline bubbles. Helix [41] goes further, observing that a single uniform sharding is suboptimal: it disaggregates attention and FFN in time, reconfiguring the same GPUs between KV-parallel attention and TP FFN phases, bridged by a single all-to-all across a flat NVLink domain. These approaches share a common assumption: a homoge- neous inter-GPU fabric. Starscream exploits a different axis of heterogeneity—the intra-GPU bandwidth hierarchy exposed by chiplet partitioning.
